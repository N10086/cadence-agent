### 2.6 顺手修掉的三处"假并发"（有前后对比）

压测第一次跑出来 cross-session 要 **31.7s**（1000 轮），`queue_wait p50=596ms`。定位发现不是锁的问题，是**事件循环被同步 CPU/IO 堵住**：

| 根因 | 现象 | 修法 | 效果 |
|---|---|---|---|
| 每次 LLM 调用都 `registry.openai_tools()` → 9 个 pydantic `model_json_schema()` | 单次 5~15ms 纯 CPU，一轮 2 次 | `ToolRegistry` 缓存；`register()` 失效 | 去掉后 cross 31.7s → 19.5s |
| trace 每行 open/append/close + 收尾重写整个文件 | 一轮 8~9 次 open（本机 open ≈ 2~4ms） | 一个 trace 一个句柄，逐行 flush；META 与首行同一次 open | 19.5s → 16.7s |
| 收尾为了补 `prompt_version` 重读+重写文件 | 一轮多 2 次 open + 整读 | 建 trace 时就算出 tier/version 传进去（`route()` 是纯函数），版本一致就不回读 | 16.7s → **4.28s**，p50 303ms → 74ms |

这三处**没有改语义**：trace 仍然逐行 flush（进程崩溃不丢已发生的步骤），schema 仍随 `register()` 刷新，`prompt_version` 仍然出现在 META/SUMMARY 里（`test_trace_uses_camel_case_and_has_summary` 仍通过）。

## 5. 遗留与偏差

- **ASSUMED: `OVERLOADED` 走 503、`SESSION_BUSY` 走 409**。契约 §4 L3 写的就是这两个码与状态码；`main._status_for` 已映射。`OVERLOADED` 是整机忙（队列满），`SESSION_BUSY` 是单会话忙 —— 后者换会话即可，不该让客户端全局退避。
- **`SESSION_BUSY` 在 SSE 里出现，而不是在 `POST /chat` 的 HTTP 响应上**。原因：`/chat` 在拿到 streamId 后就返回 202，等锁发生在后台 turn 里（这正是"循环与连接解耦"的代价）。所以协议上是：
  `POST /chat` → 202；随后该 stream 推 `error{code:SESSION_BUSY}` + `done{endedBy:busy,errorCode:SESSION_BUSY}`；HTTP 侧仍保留 409 映射（若将来改成同步等锁，直接可用）。已写进 `docs/接口文档.md` §7.2 的 L3 补充。
- **"队列"是准入控制，不是等待队列**。契约要求"满 → 503，不排队"，所以第 65 个请求不会等待，直接失败。`queue_wait_ms` 因此量的是"被接受到开始执行"的调度延迟，不是"排队时长"。50 并发时 p50≈75ms，主要来自：同会话场景本身要串行排队（20 条抢一把锁）+ trace/session 每轮仍有 2 次同步 open。
- **看门狗不取消**（与契约原文"然后取消该任务"不同）：按 L3 派工口径，取消只能有一个来源（`asyncio.timeout`），watchdog 用 `asyncio.shield` 只打栈。否则两个计时器同时到点，`CancelledError` 归因会失真。已同步修订 `docs/构建方案.md` §5.3。
- **`asyncio.Semaphore.acquire()` 本身没有单独超时**：它被"单轮 60s"整体包住，且持有者自身有 15s read 超时，所以等待有界。没有为它再加一个计时器（避免第二套超时）。
- **新增 2 个错误码**：`OVERLOADED`、`SESSION_BUSY`（加上 L2 的 `TURN_TIMEOUT`，现在共 17 个）。契约 §4 L3 点名了这两个码，属于本层授权范围；`recoverable` 都是 `true`。
- **性能修复属于 L3 范围**：三处改动都不改语义（§2.6）。如果不修，50 会话会被单线程里的 schema 重建 + 同步文件 I/O 串行化，"并发"只是纸面数字 —— 这和 L3 的目标直接冲突，所以在本层做掉。
- **剩余性能债**：每轮仍有 2 次同步 open（trace + session save）。本机 open ≈ 2~4ms，是 p50≈75ms 的一部分。彻底解决需要把落盘移出事件循环（批量/后台写），会改变"逐行 flush"的持久化语义，留给 L4/L5 决定，本层不动。
- **未验证项**：`tests/integration` 37 条仍因沙箱 `tmp_path` ACL（`PermissionError`）跑不完。本层改了 `chat.py` 的执行路径，integration 需要桌面环境补跑：


## 6. 下游可用的新接口

```python
# ---- 配置（全部可被环境变量覆盖）----
Settings.turn_queue_capacity      = 64
Settings.llm_max_concurrency      = 16
Settings.session_lock_timeout_s   = 20.0
Settings.turn_timeout_s           = 60.0   # L2 起就在；L3 的 watchdog 复用它

# ---- 准入/统计（L4 的 T_queue 与 overload_503_total 数据源）----
Runtime.queue: TurnQueue
TurnQueue.capacity / inflight / admitted_total / rejected_total
TurnQueue.stats() -> QueueStats(
    capacity, inflight, max_inflight, admitted_total, rejected_total,
    wait_p50_ms, wait_p95_ms, rejected_ratio)
TurnQueue.wait_samples() -> list[float]   # 原始毫秒样本（聚合用）

# ---- 错误码 ----
ErrorCode.OVERLOADED     -> HTTP 503   # 入口队列满，不排队
ErrorCode.SESSION_BUSY   -> HTTP 409   # 会话锁等待超时
ErrorCode.TURN_TIMEOUT   -> HTTP 504   # 整轮超时（L2 引入，L3 映射补齐）

# ---- HTTP/SSE ----
POST /chat  ->  503 {"code":503,"message":"服务繁忙…","data":{"errorCode":"OVERLOADED"}}
SSE error   -> {"code":"SESSION_BUSY","message":"这个会话的上一条消息还在处理…","suggestions":[...]}
SSE done    -> {"endedBy":"busy","errorCode":"SESSION_BUSY"}   # 等锁超时
               {"endedBy":"timeout","errorCode":"TURN_TIMEOUT"} # 单轮 60s

# ---- 编程接口（压测脚本直接复用，不走 HTTP）----
await chat.start_turn(rt, session_id, message) -> TurnHandle(stream_id, trace_id, task)
Runtime.watch(task, trace_id) -> asyncio.Task        # 看门狗；只打栈
SessionStore.acquire(session_id, timeout_s=20) -> asyncio.Lock
SessionStore.locked_count() -> int                   # 压测断言 lock_leak=0
```
