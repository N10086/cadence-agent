## 5. 遗留与偏差

- **ASSUMED: cancel = meta.clarify**。curl 实测 `PATCH /api/v1/tasks/{id}` 带 `status` 返回 200 但字段被静默忽略、version 不变，故 `task.update` 不承载取消；不加第 10 个工具、不改 Core。取消意图由 system prompt + `task.update`/`meta.clarify` description + handler 的 `NOT_IMPLEMENTED`（带 clarify 建议）三处共同兜住。
- **ASSUMED: L1-1 建议规则的落地解释**。契约写「编辑距离 <= 2 且同前缀」；`due -> due_at` 的纯 Levenshtein 距离是 3（补 `_at`），但它是契约点名的例子。实现为：公共前缀 >= 2，且（距离 <= 2 或一方是另一方的前缀）。无同前缀候选时 `suggestions=[]`，只列可用字段，不硬猜。
- **patch 内部语义**：`parse_args` 只检查顶层，`patch` 里的 `due_at` / `status` 都放行；handler 对未知 patch 键给 warning。只有 `status`/`cancel`/`cancelled` 是例外，按 L1-2 的能力边界返回 `NOT_IMPLEMENTED`（不是 L1-1 的未知字段拒绝）。
- **loop 的 F2 行为未改**：`parse_args` 的 `VALIDATION_ERROR` 目前被 `loop` 统一转成 `meta.clarify`。因此真实对话里拼错字段会停下来问用户（clarify 问题里带建议），而不是把错误信封回给模型让它自纠。L1-1 的 guard 层要求已满足；如果 L2/L3 要让模型看到 `suggestions` 后重试，需要在 `loop.py` 里区分「缺字段」与「未知字段」，那属于 L2/L3 的文件范围，本层未动。
