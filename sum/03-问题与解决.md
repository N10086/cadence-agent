# 1 ⭐⭐ Initializr 返回的版本号在 Maven Central 上不存在

### 现象

```
GET https://start.spring.io/starter.zip?bootVersion=3.3.5
→ HTTP 400 (Bad Request)
```

换成 Initializr 元数据里写的默认版本 `4.0.9.RELEASE` → 生成成功，但 Maven 报：

```
[FATAL] Non-resolvable parent POM for io.cadence:cadence-core:0.0.1-SNAPSHOT:
  The following artifacts could not be resolved:
  org.springframework.boot:spring-boot-starter-parent:pom:4.0.9.RELEASE (absent):
  Could not find artifact ... in central (https://repo.maven.apache.org/maven2)
```

### 根因

**Initializr 的版本号写法 ≠ Maven Central 的坐标。**
Initializr 内部用 `4.0.9.RELEASE` 这种 `X.Y.Z.RELEASE` 格式，
但 Maven Central 上真实发布的是 `4.1.2`（不带 `.RELEASE`）。

### 解决

不要信 Initializr 的元数据，直接查 Central：

```bash
curl https://repo.maven.apache.org/maven2/org/springframework/boot/spring-boot-starter-parent/maven-metadata.xml
```

```
latest = 4.2.0-RC1
tail   = 4.1.0, 4.1.1, 4.1.2, 4.2.0-M1, 4.2.0-M2, 4.2.0-RC1
```

用 `4.1.2`（正式版，不用 M1/RC）重新生成 → `BUILD SUCCESS`。

### 教训

**版本号永远以你实际要下载的那个仓库为准**，不要信任何"推荐版本"。

### 面试怎么讲

> "建项目时 Initializr 给我的版本号在 Maven Central 上不存在。
> 我一开始以为网络问题，去查了 Central 的 maven-metadata.xml，发现真实坐标是 `4.1.2`，
> 不带 `.RELEASE` 后缀。Initializr 的元数据格式和 Maven 坐标是两套。
>
> 这件事让我后来的习惯是：**依赖出问题先查坐标是否存在，别急着怀疑网络或代理。**"

# 2 ⭐ JDK 21 装了但进程看不见

### 现象

你已经装好了 JDK 21，但我的命令查出来还是 JDK 11：

```
java -version
openjdk version "11.0.16.1" 2022-08-12 LTS
JAVA_HOME =
```

### 根因

两个不同的问题：

1. **PATH 缓存**：DSH 进程在我的安装之前就启动了，它继承的是旧 PATH。
   新装的 JDK 在 User PATH 里，但这个进程看不到。
2. **`JAVA_HOME` 真的为空**（注册表里 Machine 和 User 都是空）——
   这是真问题，Maven 3.10 没有它会拒绝启动。

### 解决

```powershell
# 查注册表（不受进程缓存影响）
[Environment]::GetEnvironmentVariable('Path','User')

# 找到真实路径
# C:\Users\Zibo\AppData\Local\Programs\Eclipse Adoptium\jdk-21.0.13.9-hotspot

# 持久化 JAVA_HOME
[Environment]::SetEnvironmentVariable('JAVA_HOME', $jdk, 'User')
```

### 教训

**"环境变量改了但不生效" 通常不是环境变量的问题，是进程的问题。**
查注册表能看到真实值，`$env:Path` 看到的可能是缓存。

### 面试怎么讲

（这条面试价值一般，除非对方问"你环境是怎么配的"）

# 3 ⭐⭐⭐ `target/classes` 残留旧配置文件

### 现象

删掉了 `application.yml`，重新启动，**还是报同一个 YAML 解析错误**：

```
expected '<document start>', but found '<scalar>'
 in 'reader', line 5, column 1:
    spring.datasource.url=${DB_URL:j...
```

### 根因

**Maven 的增量编译不会删除已经移除的资源文件。**

```
src/main/resources/application.yml   ← 已删除
        ↓ 复制
target/classes/application.yml       ← 还在！
```

Spring Boot 从 `target/classes` 加载配置，所以读到的还是旧文件。

### 解决

```bash
mvn clean compile    # 必须先 clean
```

### 教训

**改配置文件后一定要 `clean`。** 这是 Spring Boot 项目最常见的"改了没生效"原因之一。

一条自查规则：**如果改了配置但行为完全没变，第一个怀疑对象是 `target/`。**

### 面试怎么讲

> "我删了一个配置文件，但启动还是报同样的错。
> 查了十分钟才发现 `target/classes` 里还留着旧文件 —— Maven 增量编译只增不减。
>
> 这个坑让我养成一个习惯：**改了配置先 `clean`**。
> 如果改完行为完全没变，第一反应应该是看编译产物，而不是继续改代码。"

# 4 YAML 与 properties 混用

### 现象

第 3 项的表面现象之一。两个配置文件同时存在：

```
src/main/resources/
├── application.properties   （Initializr 生成）
└── application.yml          （我加的）
```

而 `application.yml` 的内容其实是 properties 格式（`key=value`），
Spring 把它当 YAML 解析，第一行的 `key=value` 之后就开始报 scalar 错误。

### 根因

我需要确认一个基本事实：**Spring Boot 会同时加载 `.properties` 和 `.yml`，
但同一份内容不能同时用两种格式。**

### 解决

统一用 `application.properties`。理由：

- Initializr 默认生成的是 properties
- properties 没有缩进敏感问题（YAML 缩进错一格就是个坑）
- 这个项目的配置项不多，不需要 YAML 的层级

### 教训

**一个项目只用一种配置格式。** 混用不会报"你混用了"，只会报一堆看不懂的解析错误。

# 5 ⭐⭐⭐ `MEMBER OF` 对 PostgreSQL `text[]` 校验失败

### 现象

```
SemanticException: Operand of 'member of' operator must be a plural path
[SELECT t FROM Task t WHERE ... AND (:tag IS NULL OR :tag MEMBER OF t.tags) ...]
```

### 根因

`Task.tags` 映射到 PostgreSQL 原生数组 `text[]`（类型 `List<String>`）。
Hibernate 6.6 对 `MEMBER OF` 做语义检查时，认为 `t.tags` 不是"复数路径"。

**本质是 JPA 集合语义与 PostgreSQL 原生数组语义不完全对齐。**

### 解决

改用 Criteria API + PostgreSQL 原生函数：

```java
public static Specification<Task> hasTag(String tag) {
    return (root, query, cb) -> {
        if (tag == null || tag.isBlank()) {
            return cb.conjunction();
        }
        Expression<Integer> pos = cb.function(
            "array_position", Integer.class,
            root.get("tags"), cb.literal(tag.trim()));
        return cb.isNotNull(pos);
    };
}
```

同时把手写 JPQL 整体换成 `JpaSpecificationExecutor`：

```java
public interface TaskRepository extends JpaRepository<Task, String>,
                                         JpaSpecificationExecutor<Task> { }
```

### 教训

**JPQL 是数据库无关的抽象层，一旦你用上数据库特有类型（数组、JSONB），
抽象层就会漏。** 这种时候要主动下沉到原生函数，而不是硬拗 JPQL 语法。

还有一个附带收获：**动态查询条件用 Specification 比手写 JPQL 干净得多。**
原来的查询是一个 15 行的字符串，现在是若干个可组合的 `Specification`。

### 面试怎么讲

> "我用 PostgreSQL 的 `text[]` 存标签，JPA 的 `MEMBER OF` 在 Hibernate 6.6 下报语义错误 ——
> 它认为 `t.tags` 不是复数路径。
>
> 我没有继续和 JPQL 语法较劲，而是改成了 Criteria API + PostgreSQL 原生的 `array_position()` 函数。
>
> 这件事说明一个道理：**用上数据库特有类型的那一刻，JPA 的抽象就漏了。**
> 与其硬拗 JPQL，不如主动下沉到原生。副作用是顺带把整个查询从 15 行 JPQL 字符串
> 重构并成了可组合的 Specification，反而更好测了。"

# 6 ⭐⭐ Spring Boot 4 升到 Jackson 3，旧配置项全部移除

### 现象

```
Reason: failed to convert java.lang.String to
  tools.jackson.databind.SerializationFeature
  (caused by IllegalArgumentException: No enum constant
   tools.jackson.databind.SerializationFeature.adjust-dates-to-context-time-zone)
```

删掉那个配置项后又报：

```
No enum constant tools.jackson.databind.SerializationFeature.write-dates-as-timestamps
```

### 根因

**Spring Boot 4 用的是 Jackson 3**，包名从 `com.fasterxml.jackson` 变成 `tools.jackson`。
两个与日期相关的配置项都被移除了：

| 配置项 | Jackson 2 | Jackson 3 |
|---|---|---|
| `spring.jackson.serialization.write-dates-as-timestamps` | 有 | ❌ 移除（默认就是 ISO-8601） |
| `spring.jackson.deserialization.adjust-dates-to-context-time-zone` | 有 | ❌ 移除 |

### 解决

两个配置项全部删掉，加注释说明为什么不配：

```properties
# Boot 4 使用 Jackson 3（tools.jackson）。
# 这两个属性在 Jackson 3 中都已移除，且默认行为就是我们要的：
#   - write-dates-as-timestamps  → 默认输出 ISO-8601
#   - adjust-dates-to-context-time-zone → 已不存在
spring.jackson.serialization.write-dates-as-timestamps=false   # ← 也删了
```

测试代码里同样受影响：

```java
// ✗ Boot 4 里不存在
new com.fasterxml.jackson.databind.ObjectMapper()
// ✓
new tools.jackson.databind.ObjectMapper()
```

### 教训

**大版本升级时，"删配置"往往比"改配置"更常见。** 被移除的特性不会报"你用了已移除的东西"，
而是报"找不到这个枚举值"—— 错误信息指不到配置文件，得从堆栈里的包名反推。

### 面试怎么讲

> "我用了 Spring Boot 4，它已经升级到 Jackson 3，包名从 `com.fasterxml` 变成了 `tools.jackson`。
> 我照旧写了 Jackson 2 的日期配置项，报的是 `No enum constant` ——
> 错误信息完全没提配置文件在哪。
>
> 我是从堆栈里的包名 `tools.jackson` 反推出来的：**这是 Jackson 3，不是 2。**
> 查了一下确认那两个配置项在新版已经移除，而且默认行为正好是我要的 ISO-8601，删掉就行。"

# 7 ⭐⭐⭐ 时区被"吞"成 UTC

### 现象

```json
// 写入
{"dueAt": "2026-11-07T18:00:00+08:00"}

// 读出
{"dueAt": "2026-11-07T10:00:00Z"}
```

### 根因

**这不是 bug。** PostgreSQL 的 `timestamptz` 存的是 UTC 时刻，
`18:00+08:00` 和 `10:00Z` 是同一个瞬间。数据库的行为完全正确。

**真正的问题是展示层**：Agent 读到 `10:00Z` 要自己换算成北京时间，
而"下周三 18:00 前交报告"这种约束，一旦中间有个 UTC/本地时区混用，就很容易算错。

### 解决

在 DTO 转换层统一转成本地时区：

```java
private static final ZoneId OUT = ZoneId.of("Asia/Shanghai");

public static TaskResponse from(Task t) {
    return new TaskResponse(
        ...
        at(t.getStartAt()), at(t.getDueAt()), ...
    );
}

private static OffsetDateTime at(OffsetDateTime t) {
    return t == null ? null : t.atZoneSameInstant(OUT).toOffsetDateTime();
}
```

验证：

```
"dueAt": "2026-11-07T18:00:00+08:00"   ✅
```

### 教训

这是本次最值得讲的一个设计判断：

> **存储层用 UTC（正确），展示层用本地时区（友好）。**
> 两件事不冲突，冲突的是"以为它们应该是同一个值"。

而且这个决定**必须写进契约**（`openapi.yaml` 里注明"带偏移，如 2026-11-05T09:00:00+08:00"），
否则前后端各理解一半，联调时会变成玄学问题。

### 面试怎么讲

> "数据库存 UTC、接口返回东八区。这看着矛盾，其实是两件事：
>
> `timestamptz` 存 UTC 时刻是**正确的存储语义** —— 它保证同一个瞬间在任何时区读出来都一致。
> 但我的调用方是 Agent，它要解析'下周三前交报告'这种约束。
> 如果它读到的全是 UTC，它就得自己做时区换算，多一次换算就多一次算错的机会。
>
> 所以我在 DTO 转换层统一转成东八区输出，并在 OpenAPI 契约里写清楚这个约定。
> **存储要正确，展示要好用，这是两个不同层次的问题。**"

# 8 ⭐⭐⭐ RRULE 每月 31 号展开成了每月 1 号

### 现象

```
期望: [2027-01-31, 2027-02-28, 2027-03-31, 2027-04-30, 2027-05-31]
实际: [2027-02-01, 2027-03-01, 2027-04-01, 2027-05-01]
```

### 根因

`monthCandidates` 里，当 `byDay == null`（没有指定星期几）时，我直接返回了 `monthStart`
（每月 1 号），**从没读过 `dtstart` 是几号**。

设计意图是"把 dtstart 当成模板"，但那个信息在往下一层传参时丢了：

```java
// 出问题的版本
private List<LocalDate> candidatesInPeriod(LocalDate periodStart) {
    return switch (freq) {
        case DAILY -> List.of(periodStart);
        case WEEKLY -> weekCandidates(periodStart);     // ← 拿不到 dtstart
        case MONTHLY -> monthCandidates(periodStart);   // ← 拿不到 dtstart
    };
}
```

### 解决

把 `templateDate`（即 `dtstart` 的日期）显式传下去：

```java
List<LocalDate> candidates = candidatesInPeriod(cursor, startDate);

private List<LocalDate> candidatesInPeriod(LocalDate periodStart, LocalDate templateDate) {
    ...
}

private List<LocalDate> monthCandidates(LocalDate monthStart, LocalDate templateDate) {
    if (byDay == null) {
        int dom = templateDate.getDayOfMonth();
        int lastDay = monthStart.lengthOfMonth();
        return List.of(monthStart.withDayOfMonth(Math.min(dom, lastDay)));
    }
    ...
}
```

**顺带处理了"月末 31 号遇到 2 月"**：`Math.min(dom, lastDay)` → 1/31 → 2/28。
这是 RFC 5545 认可的语义，改成 `Math.min()` 比"跳过该月"更贴近用户预期。

### 教训

**纯函数最容易出的 bug，是"需要的输入没传进去"。**

`Recurrence.expand(dtstart, from, to)` 的签名里有 `dtstart`，
但内部一层层往下传的时候漏了 —— 而单看 `monthCandidates` 的代码，你完全看不出它缺了什么。

### 面试怎么讲

> "我写 RRULE 展开器的时候，'每月 31 号'展开出来全是每月 1 号。
>
> 根因是分层函数传参时把 `dtstart` 丢了：最外层的 `expand(dtstart, ...)` 有它，
> 但往下传到 `monthCandidates` 时只剩 `monthStart`，所以只能返回每月 1 号。
>
> 修的时候我改成显式传 `templateDate`，并顺手处理了'31 号遇到 2 月'这个经典问题 ——
> 取 `min(31, 当月天数)`，1/31 之后是 2/28 而不是跳过。
>
> 这个 bug 让我记牢一件事：**纯函数出问题，先怀疑输入没传全，而不是逻辑写错了。**
> 因为纯函数逻辑可以单测穷举，但漏传参数是"逻辑看起来完全正确"的那一类错误。"

# 9 ⭐⭐⭐ 修 bug 时顺手改了别处，引入了回归

### 现象

修完 #8 之后，**原本通过的 3 个 DAILY 用例全部挂掉**：

```
[ERROR] Tests run: 4, Failures: 3  -- in DAILY
```

### 根因

修 #8 时，我把 `case DAILY` 也"顺手统一"成了 `templateDate`：

```java
// 错误改动
case DAILY -> List.of(templateDate);   // ← 每日重复永远返回第一天
```

而 `periodStart` 在 DAILY 分支里是**已经按 INTERVAL 推进过**的日期，
必须用它，不能用模板日期。

### 解决

最小化改动 —— DAILY 保持原样：

```java
private List<LocalDate> candidatesInPeriod(LocalDate periodStart, LocalDate templateDate) {
    return switch (freq) {
        // DAILY：periodStart 已经按 INTERVAL 推进过，直接用它
        case DAILY -> List.of(periodStart);
        case WEEKLY -> weekCandidates(periodStart, templateDate);
        case MONTHLY -> monthCandidates(periodStart, templateDate);
    };
}
```

### 教训

这是**整个阶段最有价值的一次教训**：

> **修 bug 要最小化改动范围。**
> 如果我当时同时改了 DAILY 和 MONTHLY，测试会同时挂一片，
> 我根本分不清是哪个改动引入的问题 —— 可能要花 3 倍时间定位。

当时的正确做法应该是：只改 `monthCandidates` 和它的调用链，完全不碰 `case DAILY`。

### 面试怎么讲

> "修完'每月 31 号'的 bug，DAILY 的 3 个用例立刻挂了 —— 因为我在修的时候
> 顺手把 DAILY 分支也'统一'成了模板日期。
>
> 而 DAILY 分支里的 `periodStart` 是**已经按 INTERVAL 推进过**的日期，必须用它。
> 我的顺手改动把它变成了永远返回第一天。
>
> 这件事让我定了一条规矩：**修 bug 时只改必须改的地方。**
> 想重构就在测试全绿之后单独做。混在一起做，测试挂了你会分不清是修错了还是重构错了。"

# 10 ⭐⭐ `:batch` 路径被注册成 `/tasks/:batch`

### 现象

批量接口一直 404，报 `NoResourceFoundException`。
折腾了三轮才想到把路由表打出来：

```
ROUTE  {POST [/api/v1/tasks/:batch]}          ← 多了个斜杠
ROUTE  {POST [/api/v1/tasks/{id}:complete]}   ← 这个是对的
```

### 根因

Spring MVC 的路径规范化：

```
类级 @RequestMapping("/api/v1/tasks")
方法级 @PostMapping(":batch")
→ 规范化后 /api/v1/tasks/:batch
```

**`:batch` 被当成了一个独立的路径段 `/:batch`。**

而 `{id}:complete` 能工作，是因为 `{id}` 是一个**完整的路径段**，
`:complete` 只是这个段的后缀 —— 这是合法的。

### 试错过程

| 尝试 | 结果 |
|---|---|
| `@PostMapping(":batch")` | → `/tasks/:batch` ❌ |
| `@PostMapping("/batch")` | → `/tasks/batch`（与契约不符） ❌ |
| 加 `@RequestMapping("/api/v1")` + `@PostMapping("/tasks:batch")` | → `/tasks/tasks:batch` ❌ |
| **独立 `BatchController`，类级 `/api/v1`，方法级 `/tasks:batch`** | → `/tasks:batch` ✅ |

### 解决

```java
@RestController
@RequestMapping("/api/v1")          // ← 前缀只到 v1
public class BatchController {

    @PostMapping("/tasks:batch")    // ← 完整路径
    public BatchService.BatchResult batch(...) { ... }
}
```

### 教训

**框架的"约定优于配置"在遇到特殊路径时会失效。**
与其猜它怎么拼接，不如**把实际注册的路由表打印出来**：

```java
@Autowired @Qualifier("requestMappingHandlerMapping")
RequestMappingHandlerMapping mapping;

mapping.getHandlerMethods().forEach((info, method) ->
    System.out.println("ROUTE  " + info));
```

这个调试方法 30 秒定位问题，而我之前猜了 3 轮。

**我还把它固化成了测试**（`RouteMappingIT`），以后再出现路由问题直接看测试输出。

### 面试怎么讲

> "我要实现 Google AIP 风格的 `POST /api/v1/tasks:batch`，结果一直 404。
>
> 折腾了半天才想到：**把 Spring 实际注册的路由表打印出来。** 一看就明白了 ——
> 我写的 `:batch` 被规范化成了 `/tasks/:batch`，多了一个斜杠。
>
> 有意思的是 `{id}:complete` 能工作，因为 `{id}` 是完整路径段，冒号只是后缀。
>
> 解决办法是把批量接口拆成独立 Controller，类级前缀只到 `/api/v1`。
>
> 这件事的教训是：**别猜框架怎么拼路径，直接把路由表打出来看。**
> 我把这个打印固化成了一个测试类，以后再遇到路由问题 30 秒定位。"

# 11 ⭐⭐ 404 被兜底成 500

### 现象

调用一个不存在的接口，返回：

```json
{"code":"INTERNAL_ERROR","message":"服务内部错误","recoverable":false}
```

HTTP 500。但它应该是 404。

### 根因

Spring 抛 `NoResourceFoundException`（找不到 handler），
而我的 `GlobalExceptionHandler` 没有处理它，落到了最后的模板匹配：

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ApiError> onUnexpected(Exception ex) { ... 500 ... }
```

### 解决

```java
@ExceptionHandler(org.springframework.web.servlet.resource.NoResourceFoundException.class)
public ResponseEntity<ApiError> onNoResource(NoResourceFoundException ex) {
    return ResponseEntity.status(404)
        .body(ApiError.of(ErrorCode.NOT_FOUND, "接口不存在: " + ex.getResourcePath()));
}
```

顺带补了 `MethodArgumentTypeMismatchException`（也是 400 而不是 500）。

### 教训

**兜底处理器是双刃剑。** 它保证不泄露堆栈，
但也会把"本应是 4xx 的客户端错误"吞成 500 —— 而 500 对 Agent 意味着"不可恢复，别重试"。

一个自查清单：**列一下哪些异常会被兜底捕获**，逐个确认它该是 4xx 还是 5xx。

### 面试怎么讲

> "我给全局异常处理器加了个 `Exception.class` 的兜底，本意是防止泄露堆栈。
> 但后来发现：**访问不存在的接口返回 500 而不是 404。**
>
> 原因是没有单独处理 `NoResourceFoundException`，它落到兜底了。
>
> 这个 bug 影响的不只是状态码 —— 我的错误契约里有 `recoverable` 字段，
> 500 意味着"不可恢复，Agent 别重试"。而 404 应该是"可以先去 search 再试"。
> **吞错会让 Agent 做出错误的决策。**"

# 12 ⭐⭐⭐⭐ URL 查询串里的 `+08:00` 被解码成空格

### 现象

```
请求: GET /api/v1/tasks/{id}/occurrences?from=2026-11-01T00:00:00+08:00&to=...
服务端收到: "2026-11-01T00:00:00 08:00"    ← + 变成了空格
返回: 400 {"code":"VALIDATION_ERROR","message":"参数 from 格式不合法"}
```

### 根因

**这是 HTTP 规范，不是我代码的 bug。**

在 `application/x-www-form-urlencoded` 里（查询字符串沿用它），
`+` 被保留编码为空格。这是 1995 年 `application/x-www-form-urlencoded` 规范留下的历史包袱 ——
因为表单提交要把空格编码成 `+`。

所以时区偏移里的 `+` 必须编码成 `%2B`。

### 解决

**① 客户端**：冒烟脚本加编码函数

```powershell
function Q($iso) { return $iso -replace '\+', '%2B' }
```

**② 更重要的：写进契约**，因为 Agent 侧一定会再踩

```yaml
/api/v1/tasks/{id}/occurrences:
  get:
    description: |
      把 RRULE 展开为 [from, to] 内的具体时间点。

      ⚠️ 时区偏移里的 '+' 在查询字符串中必须编码为 %2B。
      否则按 application/x-www-form-urlencoded 规则会被解码成空格，
      OffsetDateTime 解析失败并返回 400 VALIDATION_ERROR。
      例：?from=2026-11-01T00:00:00%2B08:00&to=2026-12-01T00:00:00%2B08:00
```

### 教训

这是**本次写得最值得讲的一条**：

> 它不是"我写错了代码"，而是"**规范本身有个坑**"。
> 遇到这类问题，正确的处理不是"改完就完了"，而是**把它写进契约，让下游不再踩**。

而且它还暴露出一个更普遍的问题：**服务端返回 400 是对的，但错误信息里没告诉调用方该怎么修。**
如果错误信息是"请把 + 编码为 %2B"，我就不用查资料了。

### 面试怎么讲

> "我的 RRULE 展开接口一直 400，说时间格式不对。
> 打印出来才发现：我传的是 `2026-11-01T00:00:00+08:00`，服务端收到的是 `...00:00:00 08:00` ——
> **加号变成了空格。**
>
> 这是 `application/x-www-form-urlencoded` 的历史包袱：查询字符串里 `+` 表示空格。
> 时区的 `+` 必须编码成 `%2B`。
>
> 我修了客户端，但更重要的是**把它写进了 OpenAPI 契约的 description 里**。
> 因为我的 Agent 侧也要调这个接口，如果只修客户端不修文档，
> 下一个人（或者未来的我）一定会再踩一次。
>
> 这件事让我意识到：**接口文档的价值不在于描述正常路径，而在于提前把坑标出来。**"

# 13 ⭐⭐ `jsonb` 列类型不匹配

### 现象

```
ERROR: column "after_json" is of type jsonb
       but expression is of type character varying
```

### 根因

```java
@Column(name = "after_json", columnDefinition = "jsonb")
private String afterJson;
```

`columnDefinition` **只影响 DDL**（建表时的类型），**不影响 JDBC 绑定**。
Hibernate 看到字段是 `String`，就按 `varchar` 绑定参数，Postgres 拒绝。

### 解决

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "after_json", columnDefinition = "jsonb")
private String beforeJson;
```

**和 `Task.tags` 的 `text[]` 是同一类坑**：

```java
@JdbcTypeCode(SqlTypes.ARRAY)
@Column(name = "tags", columnDefinition = "text[]")
private List<String> tags;
```

### 教训

**用数据库特有类型时，`@JdbcTypeCode` 是必须的，`columnDefinition` 只管建表。**

### 面试怎么讲

> "我用 `jsonb` 存审计的快照，建表是 jsonb，但插入时报类型不匹配 ——
> 因为我只写了 `columnDefinition`，那只影响建表 DDL，不影响 JDBC 绑定。
>
> 必须加 `@JdbcTypeCode(SqlTypes.JSON)` 告诉 Hibernate 用 JSON 类型绑定。
>
> 这和之前 `text[]` 标签数组是同一类问题 —— **用数据库特有类型时，ORM 需要显式提示。**"

# 14 ⭐⭐⭐ 契约一致性测试"按预期失败"

### 现象

补齐功能后加了 4 个新端点（`:start` / `:reopen` / `:cancel` / `/history`），
**`ContractConformanceIT` 立刻失败了**：

```
expected: containsAll [/api/v1/tasks/{id}:start, ...]
but could not find: [/api/v1/tasks/{id}:start]
```

### 根因

这不是 bug，**这是测试在正确工作**。

我忘了把新端点写进 `specs/contracts/openapi.yaml`。

### 解决

补齐 `openapi.yaml`：

- 4 个新 path
- `VersionRequest` / `AuditEntry` 两个 schema
- `X-Trace-Id` / `X-Confirm-Token` 两个 header 参数

### 教训

**这就是"契约冻结"真正的机制。**

如果没写这个测试，`openapi.yaml` 会在一周内腐烂成一份"大致正确但没人敢信"的文档。
有了它，**改了代码忘了改文档 = CI 红**。

双向比对的意义：

```
声明 → 运行时：文档里写了的必须真的注册（否则客户端照着调会 404）
运行时 → 声明：注册了的必须写进文档（否则 Agent 不知道有这个接口）
```

只比一个方向是不够的 —— 单向比对能挡住一半的漂移。

### 面试怎么讲

> "我写了一个契约一致性测试，双向比对 OpenAPI 文档和 Spring 实际注册的路由。
>
> 后来加了 4 个新端点，**这个测试立刻失败了** —— 因为我忘了更新文档。
> 这正是我写它的目的。
>
> 如果没有这个测试，那份 OpenAPI 文档一周内就会腐烂成'大致正确但没人敢信'，
> 而 Agent 侧生成客户端全靠它。
>
> 双向比对很关键：只比一个方向只能挡住一半漂移 ——
> 挡得住'写了实现没写文档'，就挡不住'写了文档没写实现'。"

# 15 ⭐⭐ 种子数据分布与设计不符

### 现象

```json
// 期望：依赖 ~12%（约 5 条）
// 实际：with_deps = 3
```

| 版本 | with_deps | with_due | recurring |
|---|---|---|---|
| 初版 | 3 | 20 | 3 |
| 改 1 | 3 | 26 | 1 |
| 改 2 | 5 | 29 | 6 |

### 根因

**"12% 随机"在小样本（45 条）上方差太大。**

```python
if rng.random() >= 0.12:   # ← 45 条里只捞到 ~5 条触发的
    continue
pool = [x for x in tasks if x.start_at < t.start_at]   # ← 候选池还很小
```

而且前几条任务的候选池几乎是空的（没有更早的任务可以依赖）。

### 解决

改成**按结构生成，不按概率抽样**：

```python
# 按 start_at 排序，从后半段挑后继，保证前面有可选的前置
active_sorted = sorted([t for t in tasks if t.status == "TODO" and t.start_at],
                       key=lambda x: x.start_at)
n_dep_targets = max(4, int(len(active_sorted) * 0.12))
candidates = active_sorted[len(active_sorted) // 2:]
for dependent in rng.sample(candidates, min(n_dep_targets, len(candidates))):
    dep_idx = active_sorted.index(dependent)
    pool = [x for j, x in enumerate(active_sorted) if j < dep_idx]
    if pool:
        dependent.depends_on.append(rng.choice(pool).key)
```

### 教训

> **分布要看数字，不能看代码。**
> 代码里写的是"12%"，跑出来是 3 条。站在代码前面你会觉得它是对的 ——
> 12% × 45 ≈ 5.4，差不多。但实际随机抽样不是期望值，它有自己的方差。

而且这个教训有个更好的版本：**要做一个可复现的生成器，必须先定义"什么是好的分布"，再用数字验证。**
我在 `seed_generator.py` 里输出了 `summary` 字段，就是为了每次跑完能立刻看到分布对不对。

### 面试怎么讲

> "我写种子数据生成器，设计是 12% 的任务有依赖。跑出来只有 3 条。
>
> 原因是我用'独立 12% 概率'抽样 —— 在小样本（45 条）上方差太大，
> 而且前几条任务的候选池几乎是空的。
>
> 我改成按 `start_at` 排序，然后从后半段挑后继，保证前面一定有可选的前置。稳定产出 5 条链。
>
> 这件事的教训是：**做数据生成器，输出里必须有分布统计。**
> 我在 `summary` 里输出了每个维度实际的数量 —— 如果不看数字，我可能会以为生成器是对的，
> 然后拿着一个'没有依赖关系'的数据集去测求解器，得出'求解器没用'的错误结论。"

# 16 ⭐⭐ Testcontainers 每个测试类起一个容器

### 现象

第一版集成测试跑得极慢，而且每个测试类都要重新拉镜像、跑 Flyway。

### 根因

`@Container` 的默认行为：每个测试类创建一个新容器。

### 解决

用 `static` 字段 + `static {}` 块手写生命周期，实现**进程级单例**：

```java
@SuppressWarnings("resource")
protected static final PostgreSQLContainer<?> POSTGRES =
    new PostgreSQLContainer<>(DockerImageName.parse("postgres:16-alpine"))
        .withDatabaseName("cadence_test") ...;

static {
    POSTGRES.start();   // 整个 JVM 只跑一次
}

@DynamicPropertySource
static void datasource(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", POSTGRES::getJdbcUrl);
    ...
}
```

### 教训

`@Testcontainers` + `@Container` 适合快速起步，
但**多测试类共享时手动管生命周期更快**。

### 为什么不用 H2

这是 PRD 里的决策 D5，值得单独说：

```
任务用 timestamptz + text[] + jsonb
H2 对这三个的支持都不完整
→ 测试和生产的差异会藏 bug
→ 测试全绿但生产炸
```

**测试环境必须等于生产环境**，这是花几秒启动 Testcontainers 换来的。

# 17 ⭐ PowerShell 中文编码与执行策略

### 现象（三个问题）

1. **中文乱码**：`"title":"交季度报告"` 存进库变成 `äº¤å­£åº¦æ¥å`
2. **脚本无法执行**：`未对文件进行数字签名`
3. **`Invoke-RestMethod` 中文双重编码**

### 根因与解决

**① 乱码**

PowerShell 的 `GetBytes($json)` 默认用系统 ANSI（GBK），不是 UTF-8。

```powershell
# ✗
$bytes = [Text.Encoding]::GetBytes($json)
# ✓
$bytes = [System.Text.Encoding]::UTF8.GetBytes($json)
```

**② 执行策略**

```powershell
# ✓ 用 -ExecutionPolicy Bypass
powershell -NoProfile -ExecutionPolicy Bypass -File smoke.ps1

# 或者显式按 UTF-8 读进来执行（绕过文件编码问题）
$code = [System.IO.File]::ReadAllText('smoke.ps1', [System.Text.Encoding]::UTF8)
Invoke-Expression $code
```

**③ 文件本身被按 GBK 读**

`powershell -File` 会按系统默认编码读文件。中文脚本会解析失败：

```
+     title = '浜ゅ搴︽姤鍛?; priority = 'URGENT'
Unexpected token 'URGENT'
```

### 教训

**用 .NET 的 `HttpClient` 而不是 `Invoke-RestMethod`**，理由：

- `Invoke-RestMethod` 在 PowerShell 5.1 上对中文 body 会双重编码
- `HttpClient` 能精确控制字节

**验证方式**：不是看 PowerShell 控制台输出（控制台自己也可能乱），
而是**直接查数据库**：

```bash
docker exec cadence-postgres psql -U cadence -d TODO -c "SELECT title FROM task;"
→ 交季度报告   ✅
```
