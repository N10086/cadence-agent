## 二、SP2 可以直接消费的四个机制

这四样是 SP1 专门为 Agent 准备好的，**SP2 不要重复造**。

### 2.1 `recoverable` 错误分类 → 决定要不要重试

```json
{
  "code": "CONFLICT",
  "message": "任务在操作期间被修改",
  "recoverable": true,
  "suggestions": [{"tool": "task.search", "hint": "重新获取最新 version 后重试"}],
  "details": [{"taskId": "...", "expectedVersion": 0, "actualVersion": 1}]
}
```

**SP2 的 `core_client` 应该这样用**：

```python
if err["recoverable"]:
    # 可以重试，但要有次数上限（建议 2 次）
    # 优先按 suggestions 里的 tool 重新来一次
else:
    # 立即中止，不要重试
    raise UnrecoverableToolError(err)
```

**`recoverable=false` 的错误，Agent 重试一万次也不会成功。** 这是防死循环的最后一道闸。

### 2.2 乐观锁 `version` → 幻觉检测器

所有写操作必须带 `version`：

```python
# task.search 返回的每一项都有 version
{"id": "t_110", "title": "买牛奶", "version": 3, ...}

# task.update 必须回传
task.update(task_id="t_110", version=3, patch={...})
```

**编造的 id 往往配着编造的 version** —— 一次 409 就暴露了。
这也是 PRD 指标 `hallucinated_id_rate` 的实现基础。

### 2.3 幂等键 → 网络重试安全

```python
# Agent 每调用一次创建类工具，自动生成幂等键
headers = {"X-Idempotency-Key": f"{trace_id}:{step_index}"}
```

**不要由模型生成幂等键。** 由 `trace_id + step_index` 生成，天然唯一且可追溯。

### 2.4 确认令牌 → 删除两阶段

```python
# 第一次：不带令牌
DELETE /api/v1/tasks/{id}
→ 403 {"code":"CONFIRM_REQUIRED", "suggestions":[{"header":"X-Confirm-Token","value":"ct_xxx"}]}

# 第二次：带上令牌
DELETE /api/v1/tasks/{id}  +  X-Confirm-Token: ct_xxx
→ 204
```

**注意**：Agent 侧还有自己的一层 confirm（给用户看的 diff）。
**两层不冲突**，Core 这层是防直接调用方（curl、其他客户端）的。

## 三、SP2 需要自己做的事（SP1 故意不做）

| 项 | 为什么 SP1 不做 | SP2 怎么做 |
|---|---|---|
| **MCP/工具 schema** | Core 不认识工具，只认 REST | 手写 `tools.json` → 生成 Pydantic |
| **id 白名单** | Core 不关心调用方会幻觉 | guard 层：`task_id` 必须在本次 search 结果里 |
| **自然语言解析** | Core 只收结构化指令 | LLM + 规则 |
| **排期求解** | Core 无状态，求解在 Agent | SP3 纯函数 |
| **步数预算** | 不是数据结构 | `runtime/budget.py` |
| **trace** | 审计是业务日志，trace 是执行日志 | JSONL 落盘 |
| **工作日历** | 单机无需 | Agent 侧配置 `working_hours` |

## 四、一个必须知道的坑：URL 里的 `+`

上次踩过的（见 `03-问题与解决.md` #12）：

```
GET /api/v1/tasks/{id}/occurrences?from=2026-11-01T00:00:00+08:00
                                                ↑ 服务端收到的是空格

正确：from=2026-11-01T00:00:00%2B08:00
```

**已经写进 `openapi.yaml` 的 description 了**，但 Python 侧要注意：

```python
import urllib.parse
params = {"from": "2026-11-01T00:00:00+08:00"}
# ✗ httpx 的 params= 默认会正确编码，但手拼 URL 不会
url = f"{base}?from={params['from']}"   # ← 会坏

# ✓ 用 params= 让它编码
client.get(path, params=params)
```

**建议在 `core_client` 里硬化**：

```python
def _encode_params(params: dict) -> dict:
    """httpx 会自动编码，但为了防御手拼 URL 的写法，这里做显式检查。"""
    for k, v in params.items():
        if isinstance(v, str) and "+" in v:
            logger.debug("param %s contains '+', httpx will encode it as %%2B", k)
    return params
```

## 五、接口速查（Agent 会用到哪些）

| 工具 | 对应端点 | 备注 |
|---|---|---|
| `task.search` | `GET /tasks` | 6 种过滤 + `limit` |
| `task.create` | `POST /tasks` | 带幂等键 |
| `task.update` | `PATCH /tasks/{id}` | 返回 `{task, warnings}` |
| `task.complete` | `POST /tasks/{id}:complete` | 幂等 |
| `task.delete` | `DELETE /tasks/{id}` | 两阶段 |
| `task.split` | `POST /tasks:batch` | 事务性 |
| `schedule.busy` | `GET /calendar/busy` | 区间合并 |
| `plan.reschedule` | 无（**本地求解**） | 拉数据后本地算 |
| `plan.apply` | `POST /tasks:batch` | 带 version 校验 |

**注意 `PATCH` 的返回结构变了**：

```json
{
  "task": {...},
  "warnings": [{"code":"TIME_CONFLICT", "message":"...", "relatedTaskId":"..."}]
}
```

`warnings` 是给模型看的提示 —— **不是错误**。SP2 在组装工具返回值时应把它一并给模型，
让模型能说"我建好了，但它和 X 时间重叠"。

## 八、SP2 的第一个里程碑

按 PRD，W4 的出口是：

```
"你好 → 查今天的任务" 这条最短路径能跑通
```

具体拆：

1. `pyproject.toml` + uv 环境（Python 3.11）
2. `config.py`（pydantic-settings，读 `.env`）
3. `llm/base.py` + `zhipu.py`（先用一个模型，DeepSeek 后面加）
4. `tools/registry.py` + `tools/task_tools.py`（先实现 `task.search`）
5. `tools/core_client.py`（httpx client）
6. `runtime/loop.py`（单轮版本：一次 LLM 调用 → 一次工具调用 → 返回）
7. `api/chat.py`（POST /chat，先不用 SSE）

**出口标准**：

```bash
curl -X POST localhost:18000/chat -d '{"session_id":"s1","message":"今天有什么任务"}'
→ {"reply": "你今天有 3 个任务：...", "trace_id": "tr_xxx"}
```

**W4 末的硬闸门**（PRD 里写的）：

> GLM-4-Flash 连续 10 次 tool_call 成功率 < 80% → 立刻把主力模型换成 DeepSeek

**这个决定必须在 W4 做，不能拖到 W8。** 否则整个评测数据都要重跑。
