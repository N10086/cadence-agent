## 阶段 2 · 项目骨架（约 40 分钟，含 3 次失败）

### 第 1 次失败：Spring Initializr 版本号

```
GET https://start.spring.io/starter.zip?bootVersion=3.3.5
→ HTTP 400
```

查元数据：

```
bootVersion default : 4.1.2.RELEASE
available: 4.2.0.BUILD-SNAPSHOT, 4.2.0-RC1, 4.1.2.RELEASE, 4.0.9.RELEASE ...
```

用 `4.0.9.RELEASE` 生成 → Maven 报：

```
Non-resolvable parent POM: spring-boot-starter-parent:pom:4.0.9.RELEASE (absent)
```

**根因**：Maven Central 上真实坐标是 `4.1.2`，不带 `.RELEASE` 后缀。
Initializr 元数据里的写法是它自定义的，Central 上没有。

**解决**：直接查 Central 的 `maven-metadata.xml` 拿真实版本号：

```
https://repo.maven.apache.org/maven2/org/springframework/boot/spring-boot-starter-parent/maven-metadata.xml
latest = 4.2.0-RC1
tail   = 4.1.0, 4.1.1, 4.1.2, 4.2.0-M1, 4.2.0-M2, 4.2.0-RC1
```

用 `4.1.2`（正式版，不用 RC）重新生成 → `BUILD SUCCESS`。

### 结果

骨架生成，依赖解析成功。

> 详细的问题记录见 `03-问题与解决.md` #1

### 第 2 次失败：启动失败，报 YAML 解析错误

```
expected '<document start>', but found '<scalar>'
 in 'reader', line 5, column 1:
    spring.datasource.url=${DB_URL:j...
```

**根因**：Initializr 生成了 `application.properties`，我又加了 `application.yml`。
但更诡异的是 —— 两个文件都变成了 properties 格式（`key=value`），
而 Spring 把它当 YAML 解析。

**解决**：
1. 删掉 `application.yml`，统一用 `application.properties`
2. **关键**：`mvn clean` —— 因为 `target/classes` 里残留着旧的 `application.yml`，
   Maven 增量编译不会删除已移除的资源文件

### 第 3 次失败：JPA 查询校验失败

```
SemanticException: Operand of 'member of' operator must be a plural path
[SELECT ... AND (:tag IS NULL OR :tag MEMBER OF t.tags) ...]
```

**根因**：`t.tags` 映射到 PostgreSQL 原生 `text[]`，Hibernate 6.6 下
`MEMBER OF` 的语义检查过不去。

**解决**：改用 Criteria API + PostgreSQL 原生函数：

```java
Expression<Integer> pos = cb.function("array_position", Integer.class,
    root.get("tags"), cb.literal(tag.trim()));
return cb.isNotNull(pos);
```

同时把手写 JPQL 换成 `JpaSpecificationExecutor` —— 动态条件用 Specification 更自然，
也避开了 JPQL 字符串拼接的坑。

### 第 4 次失败：Jackson 属性不存在

```
No enum constant tools.jackson.databind.SerializationFeature.write-dates-as-timestamps
```

**根因**：Spring Boot 4 升级到了 **Jackson 3**（包名从 `com.fasterxml.jackson` 变成 `tools.jackson`），
`write-dates-as-timestamps` 和 `adjust-dates-to-context-time-zone` 都已移除。

**解决**：删掉这两个配置。Jackson 3 的默认行为就是 ISO-8601 输出，正是我们要的。

### 第 5 次：时区被"吞"

```
写入: dueAt = "2026-11-07T18:00:00+08:00"
读出: dueAt = "2026-11-07T10:00:00Z"
```

**根因**：不是 bug。`timestamptz` 存 UTC 是正确行为，两个值是同一个时刻。

**但需要改**：Agent 读到 `10:00Z` 要自己换算，"下周三 18:00"这类约束更容易搞错。

**解决**：`TaskResponse.from()` 里统一转到 `Asia/Shanghai`：

```java
private static OffsetDateTime at(OffsetDateTime t) {
    return t == null ? null : t.atZoneSameInstant(OUT).toOffsetDateTime();
}
```

重新验证：

```
"dueAt": "2026-11-07T18:00:00+08:00"   ✅
```

## 阶段 4 · 深化功能（约 3 小时）

### 4.1 RRULE 展开器

写了 `Recurrence`（221 行纯函数）+ `RecurrenceTest`（21 条）。

#### 第 6 次失败：每月 31 号展开成了每月 1 号

```
期望: [2027-01-31, 2027-02-28, 2027-03-31, 2027-04-30, 2027-05-31]
实际: [2027-02-01, 2027-03-01, 2027-04-01, 2027-05-01]
```

**根因**：`monthCandidates` 里 `byDay == null` 时直接返回了 `monthStart`（每月 1 号），
从没读过 `dtstart` 是几号。设计意图是"把 dtstart 当模板"，但那个信息在传参时丢了。

**解决**：`candidatesInPeriod(periodStart)` 改成 `candidatesInPeriod(periodStart, templateDate)`。

#### 第 7 次失败：修完 A 弄坏了 B（回归）

改完之后 **DAILY 的 3 个用例全挂了**。因为我顺手把 `case DAILY` 也改成了 `templateDate`，
导致每日重复永远返回第一天。

**解决**：

```java
case DAILY -> List.of(periodStart);   // periodStart 已按 INTERVAL 推进过
case WEEKLY -> weekCandidates(periodStart, templateDate);
case MONTHLY -> monthCandidates(periodStart, templateDate);
```

**这是整个阶段最有价值的一次教训**：修 bug 时最小化改动范围。
如果当时同时改了 DAILY 和 MONTHLY，测试会同时挂一片，根本分不清是哪个改坏的。

最终：**21/21 通过**。

### 4.2 任务依赖 + 环检测

`DependencyService`（198 行）+ `DependencyServiceTest`（7 条）。

**环检测用迭代式 DFS，不用递归**：

```java
Deque<String> stack = new ArrayDeque<>();
stack.push(start);
while (!stack.isEmpty()) { ... }
```

**理由**：依赖图可能很深，递归在 1000 层左右就栈溢出，显式栈没有这个上限。
这是面试里可以被追问到的点。

### 4.4 批量更新

`BatchService` + `BatchServiceTest`（5 条）。

#### 第 8 次失败：`:batch` 路径注册成了 `/tasks/:batch`

```
ROUTE  {POST [/api/v1/tasks/:batch]}    ← 多了个斜杠
ROUTE  {POST [/api/v1/tasks/{id}:complete]}  ← 这个是对的
```

**根因**：Spring MVC 把方法级路径 `":batch"` 规范化成路径段 `"/:batch"`，
拼上类级前缀 `/api/v1/tasks` 就是 `/api/v1/tasks/:batch`。
而 `{id}:complete` 能工作，是因为 `{id}` 是一个完整路径段，`:complete` 只是它的后缀。

**尝试过 3 种写法，都失败**，最后把路由表打印出来才看清：

```java
@Autowired @Qualifier("requestMappingHandlerMapping")
RequestMappingHandlerMapping mapping;

mapping.getHandlerMethods().forEach((info, method) -> System.out.println("ROUTE  " + info));
```

**解决**：拆出独立的 `BatchController`，类级前缀设成 `/api/v1`，
方法路径写 `/tasks:batch` —— 拼出来正好是 `/api/v1/tasks:batch`。

#### 第 9 次失败：`NoResourceFoundException` 被吞成 500

原来 `GlobalExceptionHandler` 没有处理 `NoResourceFoundException`（404 该由它处理），
落到了 `Exception.class` 兜底，返回 500。

**解决**：补上处理器。

## 阶段 5 · 可追溯性（约 1 小时）

### 契约一致性测试

写了 `ContractConformanceIT`：**双向**比对 `openapi.yaml` 与运行时路由。

```
声明 → 运行时：文档里写了的，必须真的注册（否则客户端照着调会 404）
运行时 → 声明：注册了的，必须写进文档（否则 Agent 不知道有这个接口）
```

### 端到端冒烟（38 项）

#### 第 10 次失败：URL 里的 `+08:00` 被解码成空格

```
请求: ?from=2026-11-01T00:00:00+08:00&to=...
服务端收到: 2026-11-01T00:00:00 08:00   ← + 变成了空格
返回: 400 VALIDATION_ERROR
```

**根因**：**HTTP 规范层面的真实陷阱**。在 `application/x-www-form-urlencoded` 里，
`+` 被保留为空格。所以查询字符串里的时区偏移必须编码成 `%2B`。

**这不是代码 bug，是规范**。所以：

1. 修了冒烟脚本（`Q()` 函数做替换）
2. **把这个约束写进了 `openapi.yaml` 的 description** —— 因为 Agent 侧调这个接口时一定会再踩

```yaml
description: |
  ⚠️ 时区偏移里的 '+' 在查询字符串中必须编码为 %2B。
  否则按 application/x-www-form-urlencoded 规则会被解码成空格，
  OffsetDateTime 解析失败并返回 400 VALIDATION_ERROR。
```

最终：**38/38 通过**。

### 6.1 V3 迁移：审计表 + 幂等表

#### 第 11 次失败：jsonb 列类型不匹配

```
column "after_json" is of type jsonb but expression is of type character varying
```

**根因**：`@Column(columnDefinition = "jsonb")` 只影响 DDL，不影响 JDBC 绑定。
Hibernate 默认按 `varchar` 绑，Postgres 拒绝。

**解决**：

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "after_json", columnDefinition = "jsonb")
private String afterJson;
```

**和 `Task.tags` 的 `text[]` 是同一类坑**：原生类型列必须显式声明 JDBC 类型。
