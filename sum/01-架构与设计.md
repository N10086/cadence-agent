```
┌───────────────────────────────────────────────┐
│  web/          Controller（薄）                │
│    TaskController      任务 + 状态 + 依赖 + 审计│
│    BatchController     批量（独立，路径原因）   │
│    CalendarController  忙闲 + RRULE 展开        │
├───────────────────────────────────────────────┤

│    TaskStateMachine     流转合法性（独立）      │
│    DependencyService    依赖 + 环检测           │
│    ConflictService      冲突 + 忙闲             │
│    BatchService         事务性批量              │
│    AuditService         审计写入                │
│    IdempotencyService   幂等                    │
│    ConfirmTokenService  确认令牌                │
├───────────────────────────────────────────────┤
│  domain/       实体与值对象                      │
│    Task / TaskDependency / AuditLog            │
│    IdempotencyRecord                          │
│    Recurrence（RRULE 解析与展开，纯函数）        │
│    TimeWindow（半开区间）                       │
├───────────────────────────────────────────────┤
│  repository/   JPA                             │
│    TaskRepository / TaskSpecifications         │
│    TaskDependencyRepository                    │
│    AuditLogRepository / IdempotencyRecordRepo  │
└───────────────────────────────────────────────┘
              ↓
        PostgreSQL 16
```

**Controller 薄到什么程度**：`TaskController.complete()` 只有一行
`return TaskResponse.from(taskService.complete(...))`。
所有判断都在 service —— 因为 Controller 无法被单元测试直接覆盖（要走 MockMvc），
而在 service 里写三行单测就能覆盖。

## 二、关键包与职责

| 包 | 文件数 | 职责 | 可否单独测 |
|---|---|---|---|
| `domain` | 10 | 实体、枚举、值对象、纯算法 | ✅ 纯单元测试 |
| `repository` | 5 | 数据访问 | 需要数据库 |
| `service` | 9 | 业务规则 | 需要数据库（集成测试） |
| `web` | 8 | HTTP 适配 | 需要全栈（MockMvc） |
| `config` | 3 | Clock / Scheduling / 其他 | — |

`Recurrence` 和 `TimeWindow` 是**纯函数**，不依赖 Spring、不依赖数据库。
这是它们能被 21 条单元测试彻底覆盖的原因。

## 三、数据模型

### 3.1 task

```sql
CREATE TABLE task (
    id            VARCHAR(36)   PRIMARY KEY,       -- UUID 字符串
    title         VARCHAR(200)  NOT NULL,
    description   TEXT,
    status        VARCHAR(16)   NOT NULL,          -- TODO/DOING/DONE/CANCELLED
    priority      VARCHAR(16)   NOT NULL,          -- LOW/NORMAL/HIGH/URGENT
    start_at      TIMESTAMPTZ,                     -- 注意是 timestamptz
    due_at        TIMESTAMPTZ,
    estimate_min  INTEGER       CHECK (5..480),
    parent_id     VARCHAR(36)   REFERENCES task,
    pinned        BOOLEAN       DEFAULT FALSE,     -- 重排期时不可动
    rrule         VARCHAR(200),                    -- iCal 子集
    tags          TEXT[]        DEFAULT '{}',
    version       BIGINT        NOT NULL DEFAULT 0,-- 乐观锁
    deleted_at    TIMESTAMPTZ,                     -- 软删除
    created_at    TIMESTAMPTZ   NOT NULL,
    updated_at    TIMESTAMPTZ   NOT NULL
);
```

**四个刻意的设计**：

1. **id 用 UUID 字符串，不用自增**
   自增 id 会让模型倾向于"猜" 1、2、3。UUID 天然不可猜，反而让模型更愿意去 search。
   *这条直接影响后面 SP2 的幻觉率指标。*

2. **时间是 `timestamptz`**
   存 UTC，出库带偏移。核心能力是时间调度，如果存储层就把时区吞掉，上层怎么修都是错的。

3. **`version` 必须在响应里**
   Agent 的 `task.update` 依赖它。拿不到就会编造，然后必然 409。

4. **`estimate_min` 带 CHECK 约束**
   5-480 分钟。约束在数据库层，防止 Agent 传出 9999 这种离谱值。

### 3.2 索引

```sql
-- 主查询：状态 + 截止期。部分索引，避免索引里一半是已删除的行
CREATE INDEX idx_task_status_due ON task (status, due_at) WHERE deleted_at IS NULL;

-- 重复规则展开
CREATE INDEX idx_task_rrule ON task (rrule) WHERE deleted_at IS NULL AND rrule IS NOT NULL;

-- 标签
CREATE INDEX idx_task_tags ON task USING GIN (tags);
```

**为什么用部分索引**：软删除的表如果不加 `WHERE deleted_at IS NULL`，
索引里会慢慢堆积一半永远查不到的垃圾行。

### 3.3 task_dependency

```sql
CREATE TABLE task_dependency (
    task_id       VARCHAR(36) NOT NULL REFERENCES task,
    depends_on_id VARCHAR(36) NOT NULL REFERENCES task,
    created_at    TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (task_id, depends_on_id),
    CONSTRAINT chk_no_self_dependency CHECK (task_id <> depends_on_id)
);
```

**复合主键**而不是自增 id：因为"同一对依赖只能存在一次"是业务约束，让数据库兜住它。
**CHECK 约束**：自己不能依赖自己，同样让数据库兜。

### 3.4 audit_log / idempotency_record

```sql
CREATE TABLE audit_log (
    id BIGSERIAL PRIMARY KEY,
    task_id VARCHAR(36) NOT NULL,
    action VARCHAR(32) NOT NULL,     -- CREATE/UPDATE/COMPLETE/START/REOPEN/CANCEL/DELETE
    actor VARCHAR(64) NOT NULL,
    trace_id VARCHAR(64),
    before_json JSONB,               -- 变更前快照
    after_json JSONB,                -- 变更后快照
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE idempotency_record (
    idem_key VARCHAR(128) PRIMARY KEY,
    task_id VARCHAR(36) NOT NULL,
    response JSONB NOT NULL,         -- 首次请求的完整响应，重放时原样返回
    created_at TIMESTAMPTZ DEFAULT now()
);
```

**为什么存快照不存 diff**：diff 需要额外的计算和格式，而快照可以直接对比、直接回放。
这个表只追加不更新，存冗余完全可接受。

## 四、五条关键设计决策

### D1 · Core 不认识 AI

Core 里搜不到 `prompt` / `llm` / `gpt`。
**验证方式**：`grep -ri "prompt\|llm\|gpt" services/cadence-core/src` 返回空。

**为什么**：这个边界守住了，Core 才能被独立测试、独立部署、独立给别人用。
守住它，项目才成立。

### D2 · 所有时间用 `OffsetDateTime` + `timestamptz`

```java
// ✓
private OffsetDateTime dueAt;
// ✗ 会把时区信息丢掉
private LocalDateTime dueAt;
```

**输出时统一转 Asia/Shanghai**（在 `TaskResponse.from()` 里）：
数据库存 UTC 是对的，但调用方读到的应该是本地语义，否则 Agent 看到 `10:00Z` 要自己换算。

### D3 · 时间基准可注入

```java
@Bean Clock clock() { return Clock.system(ZoneId.of("Asia/Shanghai")); }
```

`Recurrence` 的 21 条测试全都依赖一个**可冻结的 now**。
直接调 `OffsetDateTime.now()` 的地方，测试就无法冻结时间，"下周三到底是哪天"永远测不准。

### D4 · 状态机独立成类

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
    ┌───────┐  start   ┌───────┐  complete  ┌──────┐
    │ TODO  │─────────►│ DOING │───────────►│ DONE │
    └───────┘          └───────┘            └──────┘
        │                  │                    │
        │ cancel           │ cancel             │ reopen
        ▼                  ▼                    ▼
    ┌───────────┐     ┌───────────┐         (back to TODO)
```

明确禁止：`DONE → DOING`（必须先 reopen）、`CANCELLED → DONE`、`DONE → CANCELLED`。

**为什么抽出来**：这些约束会被 Agent 的 `task.update` 触及。散布在 service 里就没人能一眼看出全貌，
也没法做穷举测试。`TaskStateMachineTest` 的 13 条用例就是在穷举这张表。

### D5 · 错误码的 `recoverable` 字段

```json
{
  "code": "CONFLICT",
  "message": "任务 x 在操作期间被修改",
  "recoverable": true,
  "suggestions": [{"tool": "task.search", "hint": "重新获取最新 version 后重试"}],
  "details": [{"taskId": "...", "expectedVersion": 0, "actualVersion": 1}]
}
```

| 码 | HTTP | recoverable | 为什么 |
|---|---|---|---|
| VALIDATION_ERROR | 400 | ✅ true | 改参数重试可能成功 |
| CONFLICT | 409 | ✅ true | 重新拿 version 再试 |
| NOT_FOUND | 404 | ✅ true | 先 search 再试 |
| CONFIRM_REQUIRED | 403 | ✅ true | 带令牌重试 |
| ILLEGAL_TRANSITION | 422 | ❌ false | 重试永远不会成功 |
| DEPENDENCY_VIOLATION | 422 | ❌ false | 需要用户改变意图 |
| INTERNAL_ERROR | 500 | ❌ false | — |

**`recoverable=false` 的错误，Agent 不得重试** —— 这是防死循环烧钱的最后一道闸。

## 五、横切关注点

### 5.1 幂等

```
请求带 X-Idempotency-Key
    ↓
查 idempotency_record
    ├─ 命中且未过期 → 原样返回（带 Idempotent-Replayed: true 头）
    └─ 未命中 → 执行业务 → 存响应
```

24 小时 TTL，`IdempotencyService.cleanup()` 每 6 小时清一次。
**不清理的话这张表只增不减，而且每次创建都要先查它。**

### 5.2 审计

写入与业务**在同一个事务里**。

```
业务回滚 → 审计也回滚
```

**为什么这样选**：审计写入失败不会拖垮主流程（同事务，一起回滚）；
反过来的代价是留下了无法解释的痕迹比写失败更糟。对任务系统来说，后者不可接受。

`AuditServiceTest.回滚不留假账()` 专门验证了这一条。

### 5.3 冲突检测

**返回 warnings，不阻止写入。**

```json
{
  "task": {...},
  "warnings": [
    {"code": "TIME_CONFLICT", "message": "与任务「长任务」的时段重叠 60 分钟", "relatedTaskId": "..."}
  ]
}
```

**为什么不阻止**：用户可能确实想把两个任务放在同一时段（边开会边写文档）。
阻止会让 Agent 陷入无意义的纠错循环 —— 它改了，被拒，再改，再被拒。

时间占用的计算规则：
- 有 `startAt` → `[startAt, startAt + estimateMin)`
- 只有 `dueAt` → `[dueAt - estimateMin, dueAt)`
- 两个都没有 → 不参与冲突检测

## 六、RRULE 展开器（本次技术含量最高的部分）

### 支持的子集

`FREQ` (DAILY/WEEKLY/MONTHLY) · `INTERVAL` · `COUNT` · `UNTIL` · `BYDAY` · `BYSETPOS`

### 三个难点

**① 月末 31 号遇到 2 月**

```java
int dom = templateDate.getDayOfMonth();
int lastDay = monthStart.lengthOfMonth();
return List.of(monthStart.withDayOfMonth(Math.min(dom, lastDay)));
```

1/31 → 2/28（不是跳过）、3/31、4/30、5/31。

**② 每月最后一个周一**

`BYSETPOS=-1` + `BYDAY=MO`：先收集本月所有周一，再取最后一个。

```
2026-01-26, 2026-02-23, 2026-03-30, 2026-04-27, 2026-05-25, 2026-06-29
```

**③ 周期推进必须区分 DAILY 和 WEEKLY/MONTHLY**

```java
case DAILY -> List.of(periodStart);   // periodStart 已按 INTERVAL 推进过
case WEEKLY -> weekCandidates(periodStart, templateDate);
case MONTHLY -> monthCandidates(periodStart, templateDate);
```

**这一条是踩坑踩出来的**：第一版把 DAILY 也写成 `templateDate`，
结果每日重复永远只返回第一天。详见 `03-问题与解决.md` #12。

### 硬上限

- 单次展开最多 500 条（防止 COUNT 巨大撑爆内存）
- 循环最多 5000 次迭代（防死循环）

## 七、依赖图（Core 内部）

```
Controller
    ↓
Service ──→ Domain
    ↓         ↑
Repository ───┘
```

没有环。`domain` 不依赖任何上层，所以能被纯单元测试覆盖。

`TaskService` 依赖 `DependencyService`（完成任务前查前置），
`DependencyService` 不依赖 `TaskService` —— 单向，没有循环依赖。
