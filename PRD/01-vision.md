# 01 · 愿景与设计公理

> 这份文档回答两个问题：**为什么做这个**，以及**我认定的"真正的 Agent"长什么样**。

---

## 1. 为什么"AI TODO"是个错误靶子

上一轮讨论里，推荐方案给了三条改造路径：自然语言 CRUD、智能任务分解、上下文感知建议。作为学习路径它们没错，作为**作品集**它们有个致命问题：

> 这三件事，都是"一次 LLM 调用"就能完成的。它们证明你会调 API，不证明你会做 Agent。

更麻烦的是，TODO 这个领域的语义太干净了：任务、时间、优先级、状态，四个字段，零歧义、零约束冲突、零信息缺失。Agent 在里面永远不会遇到真正难的决策——**所以它永远不会展示出你处理难题的能力**。

面试官只要问一句"如果模型幻觉了一个不存在的 task_id 去删任务，会发生什么？"，这类项目就答不上来。因为作者从没想过这件事。

### 那正确的靶子是什么

不是"更强的意图理解"，而是：

> **在一个不可靠的概率组件之上，构建一个敢让它碰真实数据的确定性系统。**

这句话翻译成工程语言，就是五件事：**循环、状态、护栏、评测、可观测**。Cadence 的整个设计都围绕它们展开。

---

## 2. 真实问题定义

用户不缺记录工具。手机上装三个 TODO app 的人也照样拖延。他们真正缺的是三样东西：

| 痛点 | 用户原话 | 现有工具的做法 | Cadence 的做法 |
|---|---|---|---|
| **不知从哪开始** | "准备下周的面试" | 让你自己拆 | Agent 拆成可执行子任务，并标出依赖 |
| **排不下** | "这周病了，这些事怎么办" | 让你手动一个个改日期 | 约束求解出最小改动的方案，先给 diff 再执行 |
| **记不住** | "我怎么又拖了一周" | 一个红色角标 | 检测到拖延模式，主动提议重排，而非只提醒 |

三者的共同点：**都需要"做取舍"，而不只是"做记录"**。取舍正是 Agent 该干的活。

---

## 3. 目标用户与非目标

**目标用户**：单一的重度任务管理者（就是你自己，以及面试时的演示者）。

- 有 20-100 个活跃任务
- 任务之间有依赖、有截止期、有预估工时
- 有固定的工作时间段（比如 9:00-18:00，含午休）
- 会临时变动计划（生病、加班、出差）

**明确不是给谁用的**：

- 团队协作场景（无分享、无权限、无评论）
- 轻量随手记场景（这种场景用备忘录就够了，不需要 Agent）
- 需要多端同步的场景

## 4. Agent 设计公理

这是本文档最重要的部分。**七条公理，每条都必须能在代码里找到对应实现**，找不到就说明这个功能不该做。

### A1 · Agent 是循环，不是调用

一次 `prompt → function_call → 执行` 不叫 Agent，叫函数调用。Agent 必须有 `感知 → 规划 → 行动 → 观察 → 重规划` 的闭环，并且有**步数预算**（Cadence 定为 8 步），超预算必须优雅中止并汇报，而不是无限循环烧钱。

> 对应实现：`runtime/loop.py` 的状态机 + `budget` 模块。

### A2 · 确定性优先，模型兜底不了的地方不交给模型

LLM 只做它擅长的事：**把自然语言翻译成结构化意图**、**把结构化结果翻译成人话**。
它不做的事：**求解约束**、**判断权限**、**计算日期**。

日期计算交给 `dateutil`，排期交给约束求解器，权限交给 guard 模块。

> 这是本项目和"提示词工程"最大的区别。让 LLM 算日期是新手错误，让 LLM 做组合优化是灾难。

### A3 · 状态外置，Agent 无记忆

Agent 进程不持有业务真相。所有任务状态在 Core 的数据库里，Agent 每次需要就查。会话上下文只保留**摘要 + 当前计划 + 已确认动作**，且可被压缩。

好处：Agent 崩了重启不影响数据；会话可以重放；上下文不会无限膨胀。

> 对应实现：`runtime/session.py` 只存引用，不存实体。

### A4 · 没有评测的 Agent 不算工程

改一句 prompt，你必须有办法在 5 分钟内知道它是变好还是变坏。Cadence 的硬性要求：**任何 prompt 或工具 schema 的改动，必须过 125 条评测集，通过率不得回退**。

> 对应实现：SP4 是整个项目的 P0，且编号在 SP3 之前。

### A5 · 每一步都可观测

每次 LLM 调用和工具调用都产生一条 trace：输入、输出、token 数、耗时、成本、重试次数。没有 trace 的 bug 是不可调试的。

> 对应实现：`runtime/trace.py`，JSONL 落盘 + Web 时间线可视化。

### A6 · Agent 必须有边界

三件事不能做，除非用户明确确认：

1. 删除数据
2. 批量修改（>3 条任务）
3. 任何不可逆操作

实现方式是**双阶段**：先 `dry_run` 返回 diff，用户确认后拿 `confirm_token` 再 `apply`。

> 对应实现：`guard/confirm.py` + `plan.reschedule` 的 dry-run 模式。

### A7 · 会提问的 Agent 比会猜的 Agent 值钱

遇到歧义（"周五"是哪个周五、"报告"指哪个任务、优先级没说），正确行为是**停下来问**，不是猜一个继续跑。猜错的成本远高于多问一句。

评测里专门有一组"歧义集"来量化这个能力：**澄清率 ≥ 70%，误猜率 ≤ 15%**。

> 对应实现：`meta.clarify` 作为一等工具，而非 fallback 分支。

## 5. 三个核心剧本

### S1 · 多步意图（基础能力，但要看得出规划）

**用户**："帮我把买牛奶标记完成，然后新建一个周五前交报告的高优先级任务"

**期望行为**：
1. `task.search(keyword="买牛奶")` → 拿到 id
2. `task.complete(id)` 
3. 解析"周五" → 需要知道今天是周几，且要处理"本周五已过"的歧义
4. `task.create(title="交报告", due=..., priority=HIGH)`
5. 汇总回复

**验收点**：工具调用顺序正确；日期解析正确率 100%（用规则，不用模型）；两个操作要么都成功要么都不留半成品。

---

### S2 · 模糊任务分解

**用户**："准备下周的面试"

**期望行为**：
1. 识别出这是"需要分解"的意图（非 CRUD）
2. 调 `brain.decompose` → 用 DeepSeek 生成候选子任务
3. **关键**：生成的子任务要能落到已有时间窗口里，排不下就说明并给出建议
4. 展示草案，等用户确认后批量创建

**验收点**：分解出的子任务 ≤ 7 个（超过人类不会执行）；每个子任务有预估工时；子任务之间有依赖关系；用户拒绝时不落库。

---

### S3 · 病假重排期（旗舰场景，面试主秀）

**用户**："我这周发烧了，周三到周五基本干不了活，帮我重新排一下，能挪的挪，不能挪的别动"

**期望行为**：
1. 解析约束：不可用时间窗 `[周三 00:00, 周五 24:00)`；"能挪的挪"= 允许改期；"不能挪的别动"= 识别被 pin 的任务（有外部依赖/已承诺的）
2. 调 `plan.reschedule(dry_run=True)` → 求解器输出方案
3. 返回 diff：哪 6 个任务被移动、各移到哪天、哪 2 个任务保持不动及原因、哪 1 个任务无论怎么排都会逾期
4. 用户确认 → `apply(confirm_token)`
5. 生成人话解释："我把 3 个低优先级任务顺延到下周，2 个有外部依赖的保持原期，'交报告'最迟周五，建议今天先做"

**为什么这是旗舰**：它同时压到了意图解析、约束建模、组合优化、人机确认、结果解释五个环节，而且**有一个客观的成功标准**——所有硬约束必须满足，且移动的任务数要尽量少。

**验收点**：硬约束满足率 100%；平均移动任务数比暴力顺延少 40%；求解耗时 < 2s；解释中不出现未发生的动作。

## 6. 和"AI TODO 教程"的差异表

这张表建议直接放进 README 首屏。

| 维度 | 教程版 AI TODO | Cadence |
|---|---|---|
| 意图理解 | 单轮 function call | 多轮 + 显式澄清机制 |
| 规划 | 一次 prompt 生成 | 状态机循环 + 步数预算 + 重规划 |
| 求解 | 交给 LLM | 交给确定性算法，LLM 只做翻译 |
| 失败处理 | 无 | 错误码分类 + 自修复 + 降级 |
| 危险操作 | 直接执行 | dry-run + confirm_token |
| 评测 | 无 | 125 条数据集 + 基线对比 + CI |
| 可观测 | 无 | 全链路 trace + 成本/延迟归因 |
| 成本 | 未考虑 | 双模型路由，单轮成本 < ¥0.01 |
| 传统系统 | 玩具 CRUD | 真实领域模型：重复规则、依赖、冲突检测 |

## 7. 成功标准（产品视角）

做完之后，下面三句话必须能成立，且能被截图/数据佐证：

1. **"它能听懂带歧义的复杂指令，并且在不确定时问我，而不是瞎猜。"**（歧义澄清率 ≥ 70%）
2. **"它改数据之前会给我看 diff，我不会担心它把库删了。"**（危险操作 100% 需确认）
3. **"我改了 prompt 之后，能在 5 分钟内知道效果是变好还是变坏。"**（评测集 + CI）

如果只能做到第 1 条，这是个 demo；做到 3 条，这是个项目。
