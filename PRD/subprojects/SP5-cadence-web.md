# SP5 · cadence-web（演示界面）

> **优先级 P2 ｜ 计划 12h（W11）｜ 技术：原生 HTML + JS + SSE，无构建**

---

## 1. 概况

### 1.1 这是什么

一个**够用就好**的界面，三个使命：

1. 让 Agent 的能力**被看见**（对话流 + 工具调用实时展示）
2. 让危险操作**可确认**（diff 弹窗）
3. 让调试**可回溯**（trace 抽屉）

### 1.2 为什么不做 React

| 方案 | 工时 | 收益 |
|---|---|---|
| React + Vite + 状态管理 | 25h+ | 你能写 React，但**面试官不考这个** |
| **原生 JS + htmx 风格** | **12h** | 省下的 13h 全给 SP3/SP4 |

AI 应用岗看的是 Agent 能力，不是前端工程。**一个能跑的原生页面，好过一个半成品 React 项目。**

### 1.3 一句话原则

> 这个页面存在的唯一目的，是让面试官在 90 秒内相信"这个东西真的在思考"。

所以：**工具调用必须实时可见**。不要只显示"AI 正在输入…"，要显示 `🔧 task.search(keyword="买牛奶")`。

## 2. 范围

### In Scope
- 单页三栏布局
- 对话流（SSE 实时渲染）
- 工具调用可视化（折叠卡片）
- 待确认操作的 diff 弹窗
- 任务板（简版看板，三列）
- Trace 抽屉（时间线）
- 深色模式（可选，20 分钟的事）

### Out of Scope
- 路由、多页面
- 用户系统、登录
- 移动端适配（明确不做，桌面上演示）
- 富文本编辑器
- 拖拽排序

## 3. 需求

| ID | 需求 | 验收要点 |
|---|---|---|
| **FR-1** | 三栏布局：左=任务板，中=对话，右=Trace | 1280px 宽下不横向滚动 |
| **FR-2** | 对话输入框，Enter 发送 | 发送中禁用，显示中止按钮 |
| **FR-3** | SSE 流式渲染，逐 token 显示 | 首 token < 1.5s 出现 |
| **FR-4** | 工具调用卡片：名称 + 参数 + 耗时 + 结果摘要 | 可折叠展开看完整 JSON |
| **FR-5** | 确认弹窗：展示 moved/kept/cannot_fit 三组 diff | 未确认前不执行 |
| **FR-6** | 确认/取消后回传 token | 取消则丢弃方案，不落库 |
| **FR-7** | 任务板三列：待办 / 进行中 / 已完成 | 操作后自动刷新 |
| **FR-8** | Trace 抽屉：时间线 + 每步耗时 + 累计成本 | 点击某步可展开详情 |
| **FR-9** | 错误态：出错时显示可操作提示，不是白屏 | 网络断开有重连提示 |
| **FR-10** | 空状态引导：3 个示例指令可点击 | 降低演示门槛 |

### 非功能

| ID | 需求 | 目标 |
|---|---|---|
| NFR-1 | 首屏加载 | < 1s（本地） |
| NFR-2 | 无构建步骤 | 直接 `<script>` 引入，改完刷新即生效 |
| NFR-3 | 零依赖 | 不引 React/Vue/Tailwind CDN（断了就打不开） |

## 4. 界面设计

### 4.1 布局

```
┌────────────┬──────────────────────────┬──────────────┐
│  任务板     │        对话区             │   Trace      │
│            │                          │              │
│ ┌────────┐ │  ┌────────────────────┐  │ 00:00 USER   │
│ │ 待办 5 │ │  │ 我周三到周五发烧    │  │ 00:12 LLM    │
│ ├────────┤ │  │ 帮我重排一下        │  │ 00:48 TOOL   │
│ │ 进行 2 │ │  └────────────────────┘  │ 01:02 TOOL   │
│ ├────────┤ │  ┌────────────────────┐  │ 02:24 GUARD  │
│ │ 完成 9 │ │  │ 🔧 schedule.busy   │  │ 02:25 LLM    │
│ └────────┘ │  │    → 7 个忙时段     │  │              │
│            │  └────────────────────┘  │ 总耗时 3.4s  │
│            │  ┌────────────────────┐  │ 成本 ¥0.004  │
│            │  │ 🔧 plan.reschedule │  │              │
│            │  └────────────────────┘  │              │
│            │  ┌────────────────────┐  │              │
│            │  │ 我排了一个方案:     │  │              │
│            │  │ [查看变更并确认]    │  │              │
│            │  └────────────────────┘  │              │
└────────────┴──────────────────────────┴──────────────┘
```

### 4.2 确认弹窗（最重要的一个组件）

```
┌─ 将要修改 6 个任务 ──────────────────────────────┐
│                                                  │
│  📅 顺延（6）                                     │
│  ┌────────────────────────────────────────────┐  │
│  │ 写周报     11-05 14:00  →  11-09 10:00     │  │
│  │ 看论文     11-06 09:00  →  11-09 14:00     │  │
│  │ ...                                        │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  🔒 保持不动（7）                                 │
│  ┌────────────────────────────────────────────┐  │
│  │ 客户演示   已 pin，外部依赖                  │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  ⚠️ 无论如何都会逾期（1）                          │
│  ┌────────────────────────────────────────────┐  │
│  │ 交报告   硬截止 11-07，可用时间不足 6h        │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  硬约束检查 ✅ 全部满足                            │
│                                                  │
│         [ 取消 ]   [ 确认执行 ]                   │
└──────────────────────────────────────────────────┘
```

**三组 diff 必须分开呈现。** 尤其 `cannot_fit` 那一组——**诚实报告"排不下"，是这个产品最可信的地方**。很多 AI 产品会把所有任务都"排进去"，看起来完美，实际全是假象。

## 6. 时间路径（W11，10h）

| 时长 | 任务 |
|---|---|
| 1h | 布局骨架 + 样式（**先用死的假数据**） |
| 2h | SSE 接入 + 消息流渲染 |
| 2h | 工具调用卡片 |
| 2h | diff 弹窗 + 确认流程 |
| 2h | 任务板 + trace 抽屉 |
| 1h | 空状态 + 错误态 + 打磨 |

**做界面的第一小时必须用假数据。** 先接后端再调样式，会让你在后端小 bug 上耗掉半天。

## 7. 验收标准

### 7.1 人工验收（90 秒演示路径）

```
0:00  打开页面，输入 "我这周发烧，周三到周五干不了活，帮我重排"
0:05  看到 🔧 schedule.busy 卡片出现
0:08  看到 🔧 plan.reschedule 卡片，显示 moved=6
0:12  出现确认弹窗，三组 diff 清晰
0:20  点"确认执行"
0:25  任务板刷新，任务日期变了
0:30  打开右侧 trace，指出"这一步是护栏拦截"
0:40  输入 "准备下周的面试"
0:50  看到分解出的 4 个子任务，带工时
1:00  输入 "算了，把'看论文'删了"
1:10  看到弹出确认（不是直接删）
1:15  取消，任务还在
```

**这个 90 秒能走完，界面就算通过。**

### 7.2 检查单

- [ ] 无构建步骤，`python -m http.server` 即可打开
- [ ] 断网重连后消息不丢
- [ ] 任何后端错误都渲染成可读提示（不是 `[object Object]`）
- [ ] 确认弹窗未确认时，数据库零变更（可用 Core 的审计日志验证）
- [ ] 1280×800 下无横向滚动
- [ ] 首屏无外部 CDN 依赖（断网也能打开）

### 7.3 反向验收

- [ ] 没有引 React/Vue/jQuery
- [ ] 没有 `innerHTML` 拼接未经转义的用户输入（XSS）
- [ ] 没有把 API key 写进前端（Agent 的 key 绝不能下放浏览器）

## 8. 风险

| 风险 | 缓解 |
|---|---|
| SSE 在本地开发时 CORS 麻烦 | Agent 直接托管静态文件，省掉跨域 |
| 样式调太久 | 用一套现成的极简 CSS（比如 Pico.css 单文件），只写布局 |
| 想加功能停不下来 | 严格按 90 秒演示路径做，其余一律不做 |
