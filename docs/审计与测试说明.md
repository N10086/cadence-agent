## 0. 结论摘要

项目的主线判断是对的：Core 做确定性真相源，Agent 做概率组件的护栏，二者用 OpenAPI 隔离。但当前"已完成"的口径偏乐观：**Agent 对新建任务几乎不可写、工具 schema 自相矛盾、确认拆解实际不落库、确认令牌可以跨任务复用、tag 过滤完全失效**。这些不是"代码风格"问题，是会直接让演示失败或让评测数据失真的问题。

按严重度排序，最值得先修的 10 个：

## 1. PRD 层面的不合理之处

### P-01 "已完成"的验收口径与交付物不一致

README / PRD 声称 SP1、SP2 已完成，但：

- SP1 NFR-5 要求 `docker compose up core` 一键启动；仓库里**没有 Dockerfile**，`docker-compose.yml` 只有 postgres。
- SP1 的交付物包含 `docs/openapi.yaml`、`seed/demo.sql`、`Dockerfile`，实际是 `docs/openapi.exported.json`、`data/seed-demo-s42.json`，没有 Dockerfile。
- SP2 的 A4 要求"任何 prompt 改动必须过 125 条评测集"；SP4 未开始，仓库里没有 125 条 eval 数据集。
- M4 的"docker compose up 一键起"同样不成立。

**建议**：把"已完成"拆成"功能完成 / 契约完成 / 评测完成 / 部署完成"四列；不能一边写"已完成"，一边把 Docker、working hours、eval 留到 SP3/SP4。

### P-02 时间语义自相矛盾

PRD 02 §3.3 要求所有时间 `OffsetDateTime + timestamptz`，SP1 §4.2 又说 RRULE "展开时以任务所属时区为准，DST 也要正确"。但：

- `Task` 没有 `timezone` 字段，只有 `startAt/dueAt` 的 offset；
- `Recurrence` 用 `dtstart.getOffset()` 作为 ZoneId（固定偏移），跨 DST 后墙钟会偏一小时；
- 全库没有 per-task timezone 的存储和接口。

**建议**：二选一——要么明确"本项目只支持固定偏移，不支持 DST"并删掉相关承诺；要么在 Task 上加 IANA `time_zone` 字段，RRULE 用 `ZoneId` 展开。

### P-03 "日期解析 100% 由规则完成"没有落地

PRD A2 说日期计算交给 `dateutil`，指标 `date_parse_accuracy=100%`。实际上：

- `brain/constraints.py` 的 `parse_relative` / `parse_time_of_day` **没有被 loop 调用**；
- 日期完全由 LLM 生成 `due_at`；
- SP3 才计划"日期用规则"。

**建议**：在 SP2 就把 `constraints.parse_relative` 接到 `task.create/update` 的参数归一化里；否则 `date_parse_accuracy` 无法测量，也不该在 SP2 的完成声明里出现。

### P-04 "Core 只哑"与确认边界不一致

PRD A6 说"批量修改 >3 条需要确认"，但确认只在 Agent 的 `guard` 里：

- Core 的 `POST /tasks:batch` 本身没有确认令牌、没有条数阈值；
- 任何直接调用 Core 的客户端（curl、前端、未来的 SP3）都能一次改 100 条。

**建议**：要么在 Core 的 batch 上加 `X-Confirm-Token`/最大条数，要么把"确认只是 Agent 交互策略"写进 Non-Goals，并明确"直接调 Core 不受此保护"。

### P-05 11 个工具与 Core 能力对不上

- PRD 05 §5 说 `task.split` → `POST /tasks:batch`（事务），但 Core 的 batch **只支持更新，不支持批量创建**；SP2 实际改成 N 次创建，失败不回滚。
- `plan.apply` 映射到 `POST /tasks:batch`，但 `plan.reschedule` 返回的 `plan_id` 在 Core 没有落点；SP2 里两个工具都是桩。
- `task.split` 的 `dry_run + confirm` 语义与 Core 的 batch 事务语义不是一回事，文档却写成同一层。

**建议**：在 PRD 05 §5 明确"batch 只更新；批量创建是 Agent 的组合操作，失败按 D9 报进度"；不要再用"事务"描述 N 次创建。

### P-06 幂等承诺与并发保护不一致

FR-10 说"同一 key 重复 POST 返回首次结果，不产生重复数据"；§9.2 又承认"幂等键并发无保护，极端并发下可能建两条"。

- `idempotency_record` 是主键，但 `TaskController.create` 先查后建，两个并发请求都可能查不到；
- 幂等记录在业务事务**之外**保存，保存失败只吞掉。

**建议**：把"查幂等记录 + 创建任务 + 写幂等记录"放进同一事务，并对 key 做唯一冲突后的二次读取；否则 FR-10 只能写成"尽力而为"。

### P-07 忙闲 / 工作时间是空头承诺

SP1 In Scope 写"忙闲查询（工作时间配置）"，FR-9 写"工作时间之外 + 已有任务占用"；实际 `ConflictService.busyRanges` 只算任务，`WorkingHours.java` 不存在，文档 §9.2 也承认"Agent 侧 working_hours 配置补齐"。

**建议**：把 FR-9 降级为"仅任务占用"，working hours 明确归 SP3；或补 `working_hours` 表和查询。

### P-08 状态机文档与实现不一致

- 文档只写 `DONE/CANCELLED → reopen → TODO`；实现允许 `DOING → reopen → TODO`。
- 文档说所有写操作带 version；`cancel` 实际忽略 version。
- `complete` 在 DONE 时先返回幂等结果，不校验 version（文档有写，但与"所有写操作"冲突）。

**建议**：把"幂等路径不校验 version"写成显式例外；`cancel` 要么校验 version，要么在文档里删掉"所有写操作"。

### P-09 指标不可测量

- 125 条 eval 集不存在；
- `degraded_success_rate` 依赖"强制关闭 DeepSeek"，但只有一个 provider；
- `latency_p50 ≤1.8s`、`cost ≤¥0.01` 是按 GLM 定的，实际只有 DeepSeek，README 已承认不达标；
- `hallucinated_id_rate=0%` 的统计口径依赖 guard，但 `version` 伪造、`plan_id` 伪造没有对应统计。

**建议**：在 SP2 完成声明里把不可测指标标成"未验证"，不要用"目标"替代"实测"。

### P-10 部署与运行方式前后不一致

PRD 02 §9 列了 core/agent/web 三个服务；README 实际是手动 `mvn spring-boot:run` + `uvicorn`；`docker-compose.yml` 只有 postgres。SP5 前端在 README 里已"完成"，roadmap 却排在 W11。

**建议**：统一为"一条 compose 起 postgres；应用本地跑"，并删掉所有 `docker compose up core/agent` 的表述。

### P-11 契约版本漂移

- `docs/接口文档.md` 标 v0.3.0；
- `specs/contracts/openapi.yaml` 的 `info.version` 还是 0.2.0；
- `ErrorResponse.code` 的 enum 只有 `[400,403,404,409,422,500]`，但实际会返回 405；
- OpenAPI 描述"所有写操作必须带 version"，但 DELETE 不需要、cancel 实际不校验。

**建议**：把契约版本、错误码 enum、version 规则一起修；契约测试只校验路径，不校验这些语义，所以 CI 不会发现。

### 几个最值得展开的点

**tag 过滤为什么会恒真**：Hibernate 对 `cb.function("array_position", ...)` 的 null 处理是
`case when tags is not null then coalesce(array_position(tags, ?), 0) end is not null`。
`coalesce` 把"没找到"变成 0，`0 is not null` 恒为 true。正确写法是 `array_position(...) > 0`，
或者用原生 `tags @> ARRAY[?]`。这不是理论问题，`SP1BoundaryIT.bug_tagFilterIsNoop` 已经把它钉住。

**冲突窗口为什么错**：`Conflict` 存的是 `other.start()/other.end()`，也就是**对方任务的完整占用窗口**，
而不是 `intersection` 的起止。`overlapMinutes` 用的是交集时长，于是会出现
"窗口 09:00-17:00，重叠 30 分钟"这种自相矛盾的响应。修法是存 `inter.start()/inter.end()`，
并在 `ConflictView` 里用和 `TaskResponse` 相同的 `Asia/Shanghai` 归一化。

**列表为什么是"假分页"**：`TaskService.search` 返回全部匹配行，Controller 再 `subList`。
`hasMore` 没有配套的 offset/cursor，调用方拿到 `hasMore=true` 也无法取下一页；
1000 条任务时每次列表都把 1000 行读进 JVM，直接违背 SP1 的反向验收"没有 SELECT * 后全表内存过滤"。

### 几个最值得展开的点

**S2-02 为什么是致命的**：Core 的 `TaskResponse` 和 `docs/接口文档.md` 都明确新任务 `version=0`。
Agent 的 `TaskUpdateArgs` / `TaskCompleteArgs` 却写 `ge=1`。模型从 `task.search` 拿到 0，
一调 `task.update` / `task.complete` 就被 pydantic 拒掉，loop 把"参数不完整"转成 clarify。
表现是"AI 刚建完任务，却说自己不知道怎么改"。

**S2-03 为什么是致命的**：`TaskSplitArgs.dry_run` 默认 True。用户看到 confirm 弹窗、点确认，
`/confirm` 用令牌里存的 `args` 重新调用 handler；`args` 里没有 `dry_run=False`，
于是又执行了一次 dry-run，返回 `will_create`，`created` 为空。
admin 却按 `applied=1` 返回成功，前端显示"已执行"。

**S2-05 的边界**：令牌里其实存了 `args` 和 `versions`，但执行时完全没用。
正确做法是：`/confirm` 只执行 `pending.args`（当前确实如此），并且 loop 里带 token 的调用
必须校验 `call.arguments` 与 `pending.args` 的 task_id 一致；否则"确认 A、执行 B"是可行的。

### 4.5 SP3 / SP4 / SP5：为什么之前没写，现在补了什么

不是"暂时做不了"，而是三种不同状态：

| 子项目 | 当前状态 | 之前没写测试的原因 | 现在补的测试 |
|---|---|---|---|
| **SP3 cadence-brain** | 只有桩：`intent.py` 6 类、`constraints.py` 最小日期、`decompose` 抛 NotSupported、`proactive` 返回 []、`solver/` 空 | 没有求解器/分解/重排期实现，写"可运行测试"只能测桩，容易把桩当成能力 | `tests/sp3/test_sp3_stubs.py`：测桩是否诚实；`test_sp3_acceptance_spec.py`：求解器/分解/主动建议/重排期的验收合同，默认 skip |
| **SP4 cadence-eval** | 没有 `evals/` 包：无数据集、Runner、指标、报告、缓存 | 没有被测对象；但 PRD 自己要求"评测先于功能"，所以先冻结验收合同 | `evals/tests/test_sp4_acceptance_spec.py`：125 条/6 组、三类断言、13 指标、缓存、消融、报告、CI 时长，默认 skip |
| **SP5 cadence-web** | 有静态页面和 `e2e.js`，但只实现任务板/详情/删除确认/忙闲；**没有对话、SSE、Trace 抽屉、diff 三组** | 原任务把复审范围收窄到 SP1/SP2，我把"每个子项目"误解成"每个被复审的子项目"；这是范围遗漏，不是技术不可行 | `services/cadence-web/tests/test_static_contract.py`：静态契约；缺的对话/SSE/Trace/diff 用 xfail 钉住；`e2e.js` 继续做真实浏览器路径 |

**为什么 SP3/SP4 用 skip 而不是 xfail**：xfail 是"断言应然、当前失败"；SP3/SP4 连函数签名/模块都不存在，硬写 xfail 会变成"ImportError 也算失败"，噪声大于价值。用 skip + 明确的验收合同，实现落地后删 skip 即可激活；这比 100 条永远红的测试更可维护。

**SP5 的额外发现**：PRD 说"三栏：任务板/对话/Trace"，当前 `index.html` 只有任务板 + 右侧栏，`app.js` 没有 `EventSource`/`/chat`/`/stream`。所以 README 里"SP5 已完成"也不成立；xfail 用例就是证据。

**数量口径**：SP1 125（16 disabled）、SP2 175（25 xfail）、SP3 约 20（含 skip/xfail）、SP4 13（全 skip）、SP5 16（7 xfail）。
这些数字说明的是"边界覆盖范围"，不是"当前全绿"。
