## 一、一句话架构

```
cadence-core = "不认识 AI 的传统后端"
              = Spring Boot 4 + JPA/Hibernate + PostgreSQL 16（Flyway 管表）
```

业务上只做一件事：**管理任务**（增删改查、状态机、依赖、冲突、审计、幂等）。
它对调用方不抱任何假设——人、脚本、AI Agent 走的都是同一套 REST 接口，看同一份 `{code, message, data}` 契约。

**这个后端最特别的三点**（也是读代码时最值得注意的）：

| 设计 | 在哪 | 为什么 |
|---|---|---|
| `version` 乐观锁 | `Task`、`TaskService`、`VersionConflictException` | 让"两个调用方同时改同一条任务"变成明确可恢复的 409，而不是静默覆盖 |
| 所有写操作都有留痕 | `AuditService`、`audit_log` 表 | 出问题能回答"谁在什么时候改了什么" |
| 破坏性操作默认拒绝 | `ConfirmTokenService`、`ConfirmRequiredException` | 删除必须先拿确认令牌，防误删 |

## 二、分层与依赖方向

```
          ┌─────────────────────────────────────────────────────────┐
          │                      调用方                             │
          │    浏览器(cadence-web)       curl / Postman       Agent  │
          └───────────────┬─────────────────────────────────────────┘
                          │ HTTP + JSON  {code, message, data}
                          ▼
┌─────────────────────────────────────────────────────────────────────┐
│  web/                                                                │
│    Controller（TaskController / BatchController / CalendarController）│
│    ApiResponseAdvice（统一包装）   dto/（请求与响应形状）              │
│    error/（异常 → HTTP 状态码）                                       │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ 调用 Service 方法，只传 DTO / 基本类型
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  service/                                                            │
│    TaskService（核心业务）   TaskStateMachine（状态流转规则）          │
│    DependencyService（依赖 + 环检测）   ConflictService（冲突与忙闲）  │
│    BatchService（事务性批量）   AuditService（审计）                   │
│    IdempotencyService（幂等）   ConfirmTokenService（确认令牌）        │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ 只通过 Repository 读写
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  repository/          JPA Repository + Specification（动态条件）      │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ Hibernate 映射
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  domain/              实体与值对象：Task / TaskDependency / AuditLog… │
│                       （纯 Java + JPA 注解，不含任何 Spring 逻辑）     │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
                        PostgreSQL 16
              （表结构由 resources/db/migration 的 Flyway 脚本创建）
```

**依赖方向是单向的：web → service → repository → domain。**
反向依赖一处都没有：domain 不认识 Spring 的 Service，service 不认识 HTTP。
唯一的例外是错误类型——`service` 里会 `throw` 定义在 `web/error` 的异常，这是有意为之，见 [6.3](#63-错误是一条从上到下的通道)。

## 四、逐层详解

### 4.1 domain（领域层）

**职责**：定义"任务是什么"。这一层不依赖 Spring 的任何业务组件，只有 JPA 注解和 Java 标准库。

| 文件 | 干什么 | 关键细节 |
|---|---|---|
| `Task.java` | 任务实体，一张 `task` 表 | ① `id` 用 UUID 字符串而不是自增：自增会让"猜 id"变得容易；② 时间用 `OffsetDateTime`（对应 `timestamptz`），保留时区语义；③ `@Version Long version` 是乐观锁列；④ `deletedAt` 实现软删除，`isDeleted()` 判断；⑤ `@JdbcTypeCode(SqlTypes.ARRAY)` 把 `tags` 映射到 Postgres 的 `text[]`；⑥ `@PrePersist`/`@PreUpdate` 自动填 `createdAt`/`updatedAt` |
| `TaskStatus.java` | 4 个状态 | 状态名直接当数据库里的字符串存，人肉查库也看得懂 |
| `Priority.java` | 4 档优先级 | 同上 |
| `TaskDependency.java` | 一条依赖边 | 用**复合主键** `(taskId, dependsOnId)` 而不是自增 id：同一对依赖天然只能存在一次，由数据库兜底。`Key` 内部类实现了 `equals`/`hashCode`（复合主键必需） |
| `AuditLog.java` | 一行审计 | `beforeJson`/`afterJson` 存 JSONB。存完整快照而不是 diff：只追加不修改，冗余可接受，回放/对比都直接 |
| `IdempotencyRecord.java` | 幂等记录 | 主键就是幂等键，`response` 存首次响应体，重复请求原样返回 |
| `TimeWindow.java` | 时间区间值对象 | 半开区间 `[start, end)`，提供 `overlaps` / `intersection` / `subtract`。构造时就校验 `end > start`，非法区间根本建不出来 |
| `Recurrence.java` | RRULE 子集的解析与展开 | 手写而不引 `ical4j`。支持 `FREQ`/`INTERVAL`/`COUNT`/`UNTIL`/`BYDAY`/`BYSETPOS`；`expand()` 按周期推进并带三重安全阀（`hardCap`、`maxIterations=5000`、年份上限）。月末问题：`FREQ=MONTHLY` 遇到 2 月时取当月最后一天，而不是跳过 |

**为什么领域层这么"薄"却是核心**：因为所有"任务应该长什么样"的约束在这里被一次性定义，
往上每一层都只是在搬运和组合。

### 4.2 repository（仓储层）

**职责**：用最小的代码表达查询。这一层**不做业务判断**（比如"不能依赖自己"是 service 的事）。

| 文件 | 干什么 | 关键细节 |
|---|---|---|
| `TaskRepository.java` | 继承 `JpaRepository<Task, String>` + `JpaSpecificationExecutor<Task>` | 继承 `JpaSpecificationExecutor` 是为了让 service 能传动态条件。另外三个派生查询是"最简单场景"的捷径 |
| `TaskSpecifications.java` | 动态查询条件的拼装器 | ① 第一行硬规则：`deletedAt IS NULL`，任何调用方都绕不过去；② 关键词用 `LOWER(title) LIKE`；③ 标签用 Postgres 的 `array_position(tags, :tag)` 表达式，而不是 JPA 的 `MEMBER OF`（后者在 Hibernate 6 + `text[]` 上会抛"Operand of 'member of' operator must be a plural path"） |
| `TaskDependencyRepository.java` | 依赖查询 | `findByIdTaskId`（我依赖谁）、`findByIdDependsOnId`（谁依赖我）、`findAllByOrderBy...`（全图，给环检测和排序用） |
| `AuditLogRepository.java` | 审计查询 | 按任务倒序、按 trace 正序、最近 100 条 |
| `IdempotencyRecordRepository.java` | 幂等记录 | `@Modifying @Query` 的 `deleteOlderThan`，供定时任务调用 |

### 4.3 service（业务层）

**职责**：所有"业务上能不能这么做"的判断都在这里。这一层的每个类都可以脱离 HTTP 单独测试
（`service/` 下的 6 个测试就是这么测的）。

#### `TaskService.java` — 核心业务

| 方法 | 做什么 | 为什么这么写 |
|---|---|---|
| `search(...)` | 组合条件查询 | 把 7 个过滤条件交给 `TaskSpecifications` |
| `getOrThrow(id)` | 取任务，不存在或已删除抛 `TaskNotFoundException` | 已删除的任务对外一律"不存在" |
| `create(req, actor, traceId)` | 新建，默认状态 `TODO`，默认优先级 `NORMAL` | 写完后立刻记一条 `CREATE` 审计 |
| `patch(id, req, actor, traceId)` | 局部更新 | 先比 `version`；只有出现在请求里的字段才改 |
| `conflictWarnings(task)` | 算冲突警告 | 冲突**不阻止写入**，只返回 `warnings[]`（PRD FR-8） |
| `complete/start/reopen/cancel(id, version, …)` | 4 个状态流转 | 顺序很重要：① 已是目标状态就幂等返回；② 先过状态机；③ 再比 version。**状态错误优先于版本错误**，因为前者是调用方理解错了，后者才是并发问题 |
| `softDelete(id, …)` | 软删除 | 只写 `deletedAt`，不物理删行 |
| `assertVersionMatches(t, expected)` | 私有：版本校验 | 不匹配抛 `VersionConflictException(409)` |

#### `TaskStateMachine.java` — 状态机

一个类、4 个方法，每个方法只做一件事：**判断这个流转是否允许**。

```
        TODO ──start──► DOING ──complete──► DONE
          │               │                 │
        cancel          cancel            reopen
          ▼               ▼                 ▼
       CANCELLED ◄───────┴────────── 回到 TODO
```

明确禁止的：`DONE → start`、`CANCELLED → complete`、`DONE → cancel`。
抽出来的好处：规则集中在一处，可以穷举测试（见 `TaskStateMachineTest`），
而不会散落在 4 个 service 方法里各写一遍 if。

#### `DependencyService.java` — 依赖

- `addDependency(taskId, dependsOnId)`：先查两端存在，再查是否重复（重复则幂等返回），
  最后**环检测**：如果 `dependsOnId` 沿依赖链能回到 `taskId`，加这条边就成环 → 抛 422。
- 环检测 `reaches()` 用的是**迭代式 DFS（显式栈）**而不是递归：依赖链可能很长，递归几十层就可能栈溢出。
- `unfinishedPrerequisites(id)`：完成前检查前置是否都 `DONE`。
- `findAnyCycle()`：全图环检测，给数据灌入/评测做完整性断言。

#### `ConflictService.java` — 冲突与忙闲

- 任务占用的时间窗 = 有 `startAt` 时 `[startAt, startAt + estimateMin)`，否则 `[dueAt - estimateMin, dueAt)`。
- `detect(...)`：找与它重叠的其他**未完成**任务，算出重叠分钟数。
- `busyRanges(from, to)`：把区间内所有占用裁剪到 `[from, to]`，排序后**合并重叠/相接的段**。
- 冲突是"提示"不是"阻止"：这是刻意的产品决策，避免调用方陷入无意义的纠错循环。

#### `BatchService.java` — 批量

两步：**先全量校验版本，再统一写入**。任何一条版本不对就整批抛 `BatchConflictException(409)`，
由 `@Transactional` 保证一条都没落地。为什么不让调用方循环调单条 PATCH？因为会产生
"前 5 个成功、第 6 个失败"的中间态，用户根本没法收拾。

#### `AuditService.java` — 审计

- `record(...)` 和业务写入在**同一个事务**里：业务回滚，审计一起回滚，不会出现"记了但没改"的假账。
- `toJson(task)` 用 `TaskResponse.from` 序列化快照，保证快照和对外格式一致。
- `Action` 枚举：`CREATE / UPDATE / COMPLETE / START / REOPEN / CANCEL / DELETE / BATCH_UPDATE`。

#### `IdempotencyService.java` — 幂等

- `find(key)`：命中且未过期（24 小时）就返回记录；过期视为没有。
- `save(key, taskId, responseJson)`。
- `@Scheduled` 每 6 小时清理一次过期记录（`initialDelay=60s`）。

#### `ConfirmTokenService.java` — 确认令牌

- `issue(resourceId)`：`SecureRandom` 生成 `ct_` + 32 位十六进制，绑定任务 id 和 5 分钟有效期。
- `consume(token, resourceId)`：**取出即消费**（`tokens.remove`），无论后续校验是否通过——防止重放。
- 内存实现（`ConcurrentHashMap`），单机够用；多实例部署时需要换共享存储，这是已知限制。

#### `TaskNotFoundException.java`

服务层的最小异常：任务不存在或已删除。它故意放在 `service` 包而不是 `web/error`，
因为"目标不存在"首先是业务事实，其次才被映射成 404。

### 4.4 web（接口层）

**职责**：把 HTTP 请求翻译成 service 调用，再把结果翻译成 JSON。**不写业务规则。**

#### 三个 Controller

| 文件 | 端点 | 说明 |
|---|---|---|
| `TaskController.java` | `GET/POST /tasks`、`GET/PATCH/DELETE /tasks/{id}`、`POST /tasks/{id}:start|complete|reopen|cancel`、`GET /tasks/{id}/dependencies`、`POST/DELETE .../dependencies`、`GET /tasks/{id}/history` | 12 个端点。`create` 里处理幂等重放；`delete` 里实现两阶段确认；`history` 把审计实体转成响应 |
| `BatchController.java` | `POST /api/v1/tasks:batch` | **为什么单独成一个类**：Spring MVC 会把方法级 `":batch"` 拼成 `/{类级前缀}/:batch`，多一个斜杠。所以类级前缀设成 `/api/v1`、方法路径写 `/tasks:batch`，拼出来正好正确。这个坑写在类的注释里 |
| `CalendarController.java` | `GET /calendar/busy`、`GET /tasks/{id}/occurrences` | 忙闲、重复实例展开。空 id 视为"不存在"而不是崩溃——这是常见故障形态之一 |

#### `ApiResponse.java` + `ApiResponseAdvice.java` — 统一外壳

**这是全项目最容易"漏网"的两处之一。**

```json
{"code": 0, "message": "success", "data": {...}}
{"code": 409, "message": "version 不匹配..."}
```

- `ApiResponse`：只是个信封 record，`ok(data)` / `fail(code, message)`。
- `ApiResponseAdvice`：实现 `ResponseBodyAdvice`，在**最后序列化之前**统一处理：
  1. 正常返回值 → 包成 `code:0`
  2. `GlobalExceptionHandler` 返回的 `ApiError` → 包成 `code:状态码`
  3. Spring 内置异常产生的 `ErrorResponse` → 同样包
  4. `204` 不加体；`/v3/api-docs`、`/actuator/**` 不包装
- 坑一：Boot 4 的 JSON 转换器叫 `JacksonJsonHttpMessageConverter`，**不继承** `AbstractJackson2HttpMessageConverter`。
  如果 `supports()` 按后者判断，包装会**静默失效**——现在按类名判断。
- 坑二：`@ExceptionHandler` 只接受 `Throwable` 子类，想拦截"错误体"只能靠 `beforeBodyWrite` 识别。

#### `dto/` — 请求与响应的形状

10 个请求/响应 record + 1 个 `Warning`。约定：

- **请求**用 `@NotBlank` / `@Size` / `@Min` 等注解做第一道校验，非法请求在进入 service 前就被 400 拦下。
- **响应**用静态工厂 `from(entity)` 转换，时间统一转成 `Asia/Shanghai` 输出（库里存 UTC）。
- `Warning` 与 `ApiError` 的区别值得记：
  - `ApiError` → 请求失败，有 HTTP 错误码
  - `Warning` → 请求成功（200），但有些事情调用方应该知道（比如时间冲突）

#### `error/` — 9 个文件，两层结构

```
业务异常（VersionConflict / IllegalTransition / DependencyCycle / DependencyViolation /
          BatchConflict / ConfirmRequired）
        │ 被 GlobalExceptionHandler 接住
        ▼
   ErrorCode + ApiError（内部结构：带 recoverable / suggestions / details）
        │ 被 ApiResponseAdvice 转换
        ▼
   对外 JSON：{code: 数字状态码, message: 人话}
```

| 文件 | 被谁抛 | HTTP | 对外含义 |
|---|---|---|---|
| `VersionConflictException` | `TaskService` | 409 | 任务在你读取之后被改过，可刷新后重试 |
| `IllegalTransitionException` | `TaskStateMachine` | 422 | 状态不允许，必须由用户改变意图 |
| `DependencyCycleException` | `DependencyService` | 422 | 会成环 |
| `DependencyViolationException` | `DependencyService`/`TaskService` | 422 | 前置未完成，或自己依赖自己 |
| `BatchConflictException` | `BatchService` | 409 | 批量里有条目冲突，整批已回滚 |
| `ConfirmRequiredException` | `TaskController.delete` | 403 | 缺确认令牌，响应里带令牌 |

`GlobalExceptionHandler` 负责把上面这些**以及 Spring 自己的异常**都映射成规范状态码。几个值得注意的处理：

- `MethodArgumentNotValidException` → 400，`message` 里带上第一个出错字段名
- `HttpRequestMethodNotSupportedException` → 405，并**保持 `Allow` 头**
- `NoResourceFoundException` → 404（调错 URL 不能变成 500）
- `ObjectOptimisticLockingFailureException` → 409（Spring 默认 500，会把可恢复错误变成不可恢复）
- 兜底 `Exception` → 500，且不把堆栈抛给调用方

## 五、一次请求是怎么走完全程的

以 `PATCH /api/v1/tasks/{id}`（修改任务，带 `version`）为例：

```
1. HTTP 到达 Tomcat
2. Spring MVC 路由到 TaskController.patch
3. @Valid 校验 TaskPatchRequest
     ├─ version 为空 → MethodArgumentNotValidException → 400
     └─ 通过
4. TaskController 调 taskService.patch(id, req, actor, traceId)
5. TaskService：
     a. liveTask(id)            ← 查不到或已删除 → TaskNotFoundException → 404
     b. assertVersionMatches    ← 对不上 → VersionConflictException → 409
     c. 快照 before = audit.toJson(t)
     d. 只改请求里出现的字段
     e. repo.save(t)            ← Hibernate 自动 version+1、刷新 updatedAt
     f. audit.record(...)       ← 同一个事务里写审计
     g. conflictWarnings(t)     ← 算冲突，但只返回不阻止
6. 返回 Map{task, warnings}
7. ApiResponseAdvice 包成 {code:0, message:"success", data:{task, warnings}}
8. JSON 输出，响应头 Content-Type: application/json
```

**异常分支**（第 5 步任一处抛错）：

```
异常 → GlobalExceptionHandler 接住 → ResponseEntity<ApiError>
     → ApiResponseAdvice 识别 ApiError → {code: 409, message: "..."}
     → 事务回滚（审计一起回滚）
```

## 六、三条横切设计线

这三件事贯穿所有层，读代码时认准它们就不会迷路。

### 6.1 乐观锁：一个数字贯穿全链路

| 层 | 表现 |
|---|---|
| 表 | `task.version BIGINT NOT NULL DEFAULT 0` |
| 实体 | `@Version private Long version` |
| 请求 DTO | `TaskPatchRequest.version`（`@NotNull`）、`CompleteRequest.version` |
| 响应 DTO | `TaskResponse.version`（**必须在响应里**，否则调用方会编造一个，然后必然 409） |
| Service | `assertVersionMatches` |
| 错误 | `VersionConflictException` → 409 |

### 6.2 软删除：一条规则贯穿所有查询

`deletedAt` 非空即视为删除。`TaskSpecifications.byFilter` 的第一行永远是 `deletedAt IS NULL`；
`TaskService.liveTask` 和 `DependencyService.requireLive` 都会把已删除的任务当成"不存在"（404）。
数据库层的部分索引也与这条规则对齐。

### 6.3 错误是一条从上到下的通道

```
业务规则不满足 ──throw──► Service 里的具体异常
                              │
                              ▼
                GlobalExceptionHandler（异常 → 状态码 + ApiError）
                              │
                              ▼
                ApiResponseAdvice（ApiError → {code, message}）
                              │
                              ▼
                        调用方看到的 JSON
```

想加一种新错误，三步：`ErrorCode` 加一项 → `error/` 加一个异常类 → 在 `GlobalExceptionHandler` 里注册。
**不要**在 Controller 里自己拼 ResponseEntity 的错误体——那会绕过统一外壳。

## 七、测试代码怎么组织

### 7.1 两层测试策略

| 类型 | 怎么写 | 在哪 | 特点 |
|---|---|---|---|
| 服务层测试 | `@Autowired` Service，直接调方法 | `service/*.java` | 测业务规则，不经过 HTTP |
| 接口层测试 | `@AutoConfigureMockMvc` + `MockMvc` | `web/*IT.java` | 走完整的参数校验、JSON 序列化、异常映射 |
| 纯单元测试 | 普通 JUnit 5，不启动 Spring | `domain/*.java` | 最快，不需要 Docker |

### 7.2 `AbstractIntegrationTest` 是地基

```java
@SpringBootTest(webEnvironment = RANDOM_PORT)
public abstract class AbstractIntegrationTest {
    static final PostgreSQLContainer<?> POSTGRES = ...;   // 进程级单例
    static { POSTGRES.start(); }                         // 整个 JVM 只启一次
    @DynamicPropertySource static void datasource(...) { ... }
}
```

- **用真 Postgres（Testcontainers）而不是 H2**：任务表用了 `timestamptz` / `text[]` / `jsonb`，
  H2 对这三个支持不完整——测试和生产不一致会藏 bug。
- **单例容器**：如果每个测试类都起一个容器、跑一遍 Flyway，整个套件会慢十倍。
- 每个测试方法的 `@BeforeEach` 里 `TRUNCATE ... CASCADE` 清数据，保证用例之间互不影响。

### 7.3 跑测试时的一个坑

Maven 的 surefire **默认只匹配 `*Test`**，`*IT` 结尾的类（接口层测试）不会被 `mvn test` 跑到。
想跑全部接口层测试：

```powershell
mvn test -Dtest="ApiResponseIT,TaskControllerIT,Sp1CompletionIT,WebUiIT,ContractConformanceIT,OpenApiExportIT,RouteMappingIT" -Dsurefire.failIfNoSpecifiedTests=false
```

> 如果要让 `mvn verify` 自动跑这些 IT，需要加 failsafe 插件——目前还没加，是已知待办。

## 附：这套架构里最值得讲的几个点（面试可直接用）

1. **`version` 是幻觉检测器**：编造的 id 往往配着编造的 version，一次 409 就暴露了。
2. **冲突只警告不阻止**：阻止会让调用方陷入无意义的纠错循环；这是产品决策不是技术妥协。
3. **批量必须由后端做事务**，不能让调用方循环调单条——否则会产生无法收拾的中间态。
4. **删除两阶段**：令牌 5 分钟过期、单次有效，且 `consume` 是"取出即消费"，防重放。
5. **审计和业务同事务**：宁可写失败，也不要留下无法解释的痕迹。
6. **部分索引**：所有业务索引都带 `WHERE deleted_at IS NULL`，软删除不会拖慢查询。
7. **环检测用迭代式 DFS**：依赖链可能很深，递归有栈溢出风险。
8. **统一外壳的坑**：Boot 4 的 Jackson 3 转换器类名变了，`supports()` 判断写错会静默失效。
