## 一、通用约定

### 1.1 服务地址

| 服务 | 基础地址 | 状态 |
|---|---|---|
| `cadence-core`（任务后端） | `http://localhost:18080` | ✅ 已实现 |
| `cadence-agent`（对话后端） | `http://localhost:18000` | ✅ 已实现（SP2） |

**下文所有「请求路径」都只写 `/api/v1/...` 部分。** 实际请求时按上表拼上基础地址，例如：

```
GET http://localhost:18080/api/v1/tasks?limit=20
```

本地开发统一用 `localhost`，不写死 IP。前端 `services/cadence-web` 的基础地址按这个顺序取：

1. 页面由 Core 托管时（`http://localhost:18080/ui/...`）→ 走同源，自动就是 `http://localhost:18080`
2. 地址栏带 `?api=http://host:port` → 用这个值（单独起静态服务器时用）
3. 其它情况（直接打开 `file://`）→ 回落到 `http://localhost:18080`
4. 控制台里随时可以 `cadence.setBaseUrl('http://192.168.1.5:18080')` 临时改

后端对 `/api/**` 放开了 CORS（允许任意来源、GET/POST/PATCH/DELETE），所以前三种方式都能用。

### 1.2 请求头

| 请求头 | 是否必填 | 说明 |
|---|---|---|
| `Content-Type` | 带请求体时必填 | 固定 `application/json; charset=utf-8` |
| `X-Actor` | 否 | 调用方标识，写入审计日志。默认 `anonymous`；Agent 传 `agent`，前端传 `web` |
| `X-Trace-Id` | 否 | 调用方 trace 号，用于把一次对话的多个操作串起来 |
| `X-Idempotency-Key` | 否 | 幂等键，仅「新增任务」使用。同键重复请求返回首次结果，24 小时有效 |
| `X-Confirm-Token` | 否 | 删除任务的确认令牌，见 [3.5](#35-删除任务两步确认) |

### 1.3 统一响应格式

**所有接口**（成功和失败）都返回下面这个外壳，**没有例外**：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | number | `0` 表示成功；**失败时等于 HTTP 状态码**（400/403/404/409/422/500） |
| `message` | string | 提示信息。成功固定 `success`；失败是可读的中文原因 |
| `data` | object \| array | 业务数据。**失败时该字段不存在**（整个字段省略，不是 `null`） |

约定细节：

- **HTTP 状态码与 `code` 一致**，成功是 `200`/`201`/`204`，失败是 `4xx`/`5xx`。
  前端可以只看 `response.ok`，也可以只看 `code`，两种写法都能判断成功失败。
- **只有一种例外**：`204 No Content` 的响应没有响应体，例如删除依赖、删除任务成功。
  「删除任务」第一步返回的是 403，`data` 里有确认令牌，见 [3.5](#35-删除任务两步确认)。
- `data` 的结构由每个接口单独定义，**下文每个接口都只描述 `data` 内部的字段**。
- 字段命名统一 `camelCase`；时间统一 `ISO-8601` 带时区偏移，服务端一律按 `Asia/Shanghai` 输出，
  例如 `2026-11-05T09:00:00+08:00`。

**成功响应样例**（任务列表）：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "hasMore": false,
    "total": 0
  }
}
```

**失败响应样例**（版本冲突）：

```json
{
  "code": 409,
  "message": "任务 6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11 的 version 不匹配：期望 999，实际 3"
}
```

### 1.4 枚举取值

| 枚举 | 取值 | 含义 |
|---|---|---|
| `status` | `TODO` | 待办（新建任务的默认状态） |
| | `DOING` | 进行中 |
| | `DONE` | 已完成 |
| | `CANCELLED` | 已取消 |
| `priority` | `LOW` | 低 |
| | `NORMAL` | 普通（默认） |
| | `HIGH` | 高 |
| | `URGENT` | 紧急 |

### 1.5 时间与查询参数的两个坑

- **查询参数里的 `+` 必须编码成 `%2B`。** 不编码会被当成空格，`from=...+08:00` 会变成 `... 08:00` 解析失败并返回 400。
  ```text
  ✓ /api/v1/calendar/busy?from=2026-11-04T00:00:00%2B08:00&to=2026-11-05T00:00:00%2B08:00
  ✗ /api/v1/calendar/busy?from=2026-11-04T00:00:00+08:00&to=2026-11-05T00:00:00+08:00
  ```
  用 `fetch` 的 `URLSearchParams` 或 `httpx` 的 `params=` 会自动编码，不要手拼 URL。
- **`version` 是乐观锁版本号。** 所有修改类接口都必须回传，它必须来自最近一次查询结果；用旧版本会得到 409。

### 任务对象（下文多处引用）

下文把 `data` 里的任务对象统一记为 **Task**，完整字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 任务 id，UUID 字符串 |
| `title` | string | 标题，1-200 字 |
| `description` | string | 描述，可为空（空字段不出现在响应里） |
| `status` | string | `TODO` / `DOING` / `DONE` / `CANCELLED` |
| `priority` | string | `LOW` / `NORMAL` / `HIGH` / `URGENT` |
| `startAt` | string | 开始时间 ISO-8601 带偏移，可为空 |
| `dueAt` | string | 截止时间 ISO-8601 带偏移，可为空 |
| `estimateMin` | number | 预估耗时（分钟），5-480，可为空 |
| `parentId` | string | 父任务 id，可为空 |
| `pinned` | boolean | 是否「固定」：重排期时不许移动 |
| `rrule` | string | 重复规则（iCal RRULE 子集），可为空 |
| `tags` | array\<string\> | 标签 |
| `version` | number | 乐观锁版本号，**修改时必须回传** |
| `createdAt` | string | 创建时间 |
| `updatedAt` | string | 最后更新时间 |

**Task 样例：**

```json
{
  "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
  "title": "交季度报告",
  "status": "TODO",
  "priority": "URGENT",
  "dueAt": "2026-11-07T18:00:00+08:00",
  "estimateMin": 360,
  "pinned": false,
  "rrule": "FREQ=WEEKLY;BYDAY=WE;COUNT=3",
  "tags": ["work"],
  "version": 0,
  "createdAt": "2026-11-05T09:12:31+08:00",
  "updatedAt": "2026-11-05T09:12:31+08:00"
}
```

> 说明：值为 `null` 的字段（如没有描述时的 `description`）**不会出现在 JSON 里**，前端按「字段可能不存在」处理。

## 三、任务管理

### 3.1 任务列表查询

- **接口名称**：任务列表查询
- **接口描述**：按条件分页查询任务。**已删除的任务永不返回。** 所有条件可以组合，条件之间是「与」的关系。
- **请求路径**：`/api/v1/tasks`
- **请求方式**：`GET`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 否 | 按任务 id 精确匹配 |
| `keyword` | string | 否 | 标题模糊匹配，忽略大小写 |
| `status` | string | 否 | 状态过滤：`TODO`/`DOING`/`DONE`/`CANCELLED` |
| `priority` | string | 否 | 优先级过滤：`LOW`/`NORMAL`/`HIGH`/`URGENT` |
| `dueBefore` | string | 否 | 截止时间 ≤ 该时间，ISO-8601 带偏移 |
| `dueAfter` | string | 否 | 截止时间 ≥ 该时间，ISO-8601 带偏移 |
| `tag` | string | 否 | 标签过滤，精确匹配其中一个标签 |
| `limit` | number | 否 | 最多返回条数，1-50，默认 20；超出范围按边界值处理 |

- 排序：按 `dueAt` 升序（没有截止时间的排最后），再按 `createdAt` 升序。
- 无请求参数时可全部省略；**全部省略等价于「查询全部任务，最多 20 条」**。

**响应参数说明**（`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| `items` | array | 任务列表（元素结构见 [Task](#任务对象下文多处引用)） |
| `hasMore` | boolean | 是否还有更多：结果被 `limit` 截断时为 `true` |
| `total` | number | 满足条件的总条数（未截断前的数量） |

**响应数据样例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [
      {
        "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
        "title": "交季度报告",
        "status": "TODO",
        "priority": "URGENT",
        "dueAt": "2026-11-07T18:00:00+08:00",
        "estimateMin": 360,
        "pinned": false,
        "tags": ["work"],
        "version": 0,
        "createdAt": "2026-11-05T09:12:31+08:00",
        "updatedAt": "2026-11-05T09:12:31+08:00"
      }
    ],
    "hasMore": true,
    "total": 37
  }
}
```

**错误情况**：参数格式错误（如 `limit=abc`、时间不是 ISO-8601）返回 `400`。

### 3.2 任务详情查询

- **接口名称**：任务详情查询
- **接口描述**：查询单个任务，同时返回它的前置任务、后继任务，以及与其它任务的时间冲突。
- **请求路径**：`/api/v1/tasks/{id}`
- **请求方式**：`GET`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id，路径参数 |

**响应参数说明**（`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| `task` | object | 任务本体，结构见 [Task](#任务对象下文多处引用) |
| `dependsOn` | array\<string\> | 我的前置任务 id 列表（我依赖谁） |
| `blocks` | array\<string\> | 我的后继任务 id 列表（谁依赖我） |
| `conflicts` | array | 与我在时间上重叠的其它任务，可能为空数组 |

**`conflicts` 元素说明**

| 参数名 | 类型 | 说明 |
|---|---|---|
| `taskId` | string | 冲突任务的 id |
| `title` | string | 冲突任务标题 |
| `priority` | string | 冲突任务优先级 |
| `overlapStart` | string | 与冲突任务时间重叠的起始时间 |
| `overlapEnd` | string | 重叠的结束时间 |
| `overlapMinutes` | number | 重叠时长（分钟） |

**响应数据样例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "task": {
      "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
      "title": "写周报",
      "status": "DOING",
      "priority": "HIGH",
      "startAt": "2026-11-05T10:00:00+08:00",
      "estimateMin": 60,
      "pinned": false,
      "tags": [],
      "version": 2,
      "createdAt": "2026-11-04T20:00:00+08:00",
      "updatedAt": "2026-11-05T09:30:00+08:00"
    },
    "dependsOn": ["9b2c7f80-1a3e-4e25-8b6c-2f9c1d4a5e70"],
    "blocks": [],
    "conflicts": [
      {
        "taskId": "c3d4e5f6-a7b8-4c9d-8e0f-1a2b3c4d5e6f",
        "title": "客户演示",
        "priority": "URGENT",
        "overlapStart": "2026-11-05T10:00:00+08:00",
        "overlapEnd": "2026-11-05T10:30:00+08:00",
        "overlapMinutes": 30
      }
    ]
  }
}
```

**错误情况**：任务不存在或已删除返回 `404`。

### 3.3 新增任务

- **接口名称**：新增任务
- **接口描述**：创建一个任务，新建任务状态固定为 `TODO`。
- **请求路径**：`/api/v1/tasks`
- **请求方式**：`POST`
- **响应格式**：`application/json`

**请求参数说明**（请求体 `application/json`）

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `title` | string | 是 | 标题，1-200 字，不能全空格 |
| `description` | string | 否 | 描述，最多 4000 字 |
| `priority` | string | 否 | 优先级，默认 `NORMAL` |
| `startAt` | string | 否 | 开始时间，ISO-8601 带偏移 |
| `dueAt` | string | 否 | 截止时间，ISO-8601 带偏移 |
| `estimateMin` | number | 否 | 预估耗时（分钟），5-480 |
| `parentId` | string | 否 | 父任务 id |
| `pinned` | boolean | 否 | 是否固定，默认 `false` |
| `rrule` | string | 否 | 重复规则，最多 200 字符，如 `FREQ=WEEKLY;BYDAY=WE;COUNT=3` |
| `tags` | array\<string\> | 否 | 标签列表 |

**请求头（可选，但强烈建议 Agent 传）**

| 请求头 | 说明 |
|---|---|
| `X-Idempotency-Key` | 幂等键。同一个键重复请求**只会创建一条任务**，第二次返回的仍是第一次的结果，并且响应头带 `Idempotent-Replayed: true` |

**响应参数说明**（`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| （整个对象） | object | 新建任务的完整 [Task](#任务对象下文多处引用)，`version` 为 `0` |

响应头：

| 响应头 | 说明 |
|---|---|
| `Idempotent-Replayed` | 仅幂等重放时出现，值为 `true` |

**请求数据样例**

```json
{
  "title": "交季度报告",
  "priority": "URGENT",
  "dueAt": "2026-11-07T18:00:00+08:00",
  "estimateMin": 360,
  "tags": ["work"]
}
```

**响应数据样例**（HTTP 201）

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
    "title": "交季度报告",
    "status": "TODO",
    "priority": "URGENT",
    "dueAt": "2026-11-07T18:00:00+08:00",
    "estimateMin": 360,
    "pinned": false,
    "tags": ["work"],
    "version": 0,
    "createdAt": "2026-11-05T09:12:31+08:00",
    "updatedAt": "2026-11-05T09:12:31+08:00"
  }
}
```

**错误情况**

| 状态码 `code` | 场景 |
|---|---|
| `400` | `title` 缺失/超长、`estimateMin` 不在 5-480、时间格式错误、请求体不是合法 JSON |

### 3.4 修改任务

- **接口名称**：修改任务
- **接口描述**：局部修改任务字段。**只修改请求体里出现的字段**，没出现的字段保持不变。
- **请求路径**：`/api/v1/tasks/{id}`
- **请求方式**：`PATCH`
- **响应格式**：`application/json`

**请求参数说明**

路径参数：

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id |

请求体（`application/json`）：

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `version` | number | 是 | 乐观锁版本号，取自最近一次查询 |
| `title` | string | 否 | 标题，最多 200 字 |
| `description` | string | 否 | 描述 |
| `priority` | string | 否 | 优先级 |
| `startAt` | string | 否 | 开始时间 |
| `dueAt` | string | 否 | 截止时间 |
| `estimateMin` | number | 否 | 预估耗时（分钟），5-480 |
| `pinned` | boolean | 否 | 是否固定 |
| `rrule` | string | 否 | 重复规则，最多 200 字符 |
| `tags` | array\<string\> | 否 | 标签列表（**整体替换**，不是追加） |

**响应参数说明**（`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| `task` | object | 修改后的完整任务，结构见 [Task](#任务对象下文多处引用) |
| `warnings` | array | 非致命提示。**修改成功但仍可能有时间冲突**时非空；没有则为 `[]` |

**`warnings` 元素说明**

| 参数名 | 类型 | 说明 |
|---|---|---|
| `code` | string | 提示类型，目前只有 `TIME_CONFLICT` |
| `message` | string | 可读提示，如「与任务「客户演示」的时段重叠 30 分钟」 |
| `relatedTaskId` | string | 与之冲突的任务 id |

> **重要：时间冲突只是警告，不会阻止修改。** 后端返回 HTTP 200，前端/Agent 应把 `warnings` 展示给用户，
> 而不是当成失败重试。

**请求数据样例**

```json
{
  "version": 0,
  "startAt": "2026-11-05T12:00:00+08:00",
  "priority": "HIGH"
}
```

**响应数据样例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "task": {
      "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
      "title": "交季度报告",
      "status": "TODO",
      "priority": "HIGH",
      "startAt": "2026-11-05T12:00:00+08:00",
      "dueAt": "2026-11-07T18:00:00+08:00",
      "estimateMin": 360,
      "pinned": false,
      "tags": ["work"],
      "version": 1,
      "createdAt": "2026-11-05T09:12:31+08:00",
      "updatedAt": "2026-11-05T14:03:10+08:00"
    },
    "warnings": [
      {
        "code": "TIME_CONFLICT",
        "message": "与任务「客户演示」的时段重叠 30 分钟",
        "relatedTaskId": "c3d4e5f6-a7b8-4c9d-8e0f-1a2b3c4d5e6f"
      }
    ]
  }
}
```

**错误情况**

| 状态码 `code` | 场景 | 前端处理建议 |
|---|---|---|
| `400` | 参数不合法 | 提示用户并高亮字段 |
| `404` | 任务不存在 | 提示「任务已不存在」并刷新列表 |
| `409` | `version` 不匹配（别人刚改过） | 重新查询拿到新 `version` 后重试 |

### 3.5 删除任务（两步确认）

- **接口名称**：删除任务
- **接口描述**：软删除任务。被删除的任务在之后的查询里一律 `404`。
  因为删除不可撤销，接口设计成**两步**：先拿确认令牌，再带令牌真正删除。
- **请求路径**：`/api/v1/tasks/{id}`
- **请求方式**：`DELETE`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id（路径参数） |
| `X-Confirm-Token` | string | 第二步必填 | 第一步返回的确认令牌（请求头） |

**请求头 `X-Confirm-Token` 说明**

| 取值 | 行为 |
|---|---|
| 不带 / 令牌无效 / 令牌与其他任务不匹配 | 返回 `403`，`data` 里给一个**新的**确认令牌 |
| 有效令牌（5 分钟内、且只属于当前任务） | 真正删除，返回 `204` |

- 令牌 **5 分钟**过期，**只能用一次**。

**第一步响应参数说明**（403，`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| `confirmToken` | string | 确认令牌，形如 `ct_1a2b...` |
| `expiresInSeconds` | number | 有效期秒数，固定 `300` |
| `snapshot` | object | 将被删除任务的快照，结构见 [Task](#任务对象下文多处引用)，供前端弹窗展示 |

**第一步响应数据样例**（HTTP 403）

```json
{
  "code": 403,
  "message": "删除是破坏性操作，需要确认。请带上 X-Confirm-Token 重新请求。",
  "data": {
    "confirmToken": "ct_3f9a1c7b52e84d60a1b2c3d4e5f60718",
    "expiresInSeconds": 300,
    "snapshot": {
      "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
      "title": "交季度报告",
      "status": "TODO",
      "priority": "URGENT",
      "version": 3,
      "pinned": false,
      "tags": ["work"],
      "createdAt": "2026-11-05T09:12:31+08:00",
      "updatedAt": "2026-11-06T10:00:00+08:00"
    }
  }
}
```

**第二步响应**：HTTP `204`，**没有响应体**。

**错误情况**

| 状态码 `code` | 场景 |
|---|---|
| `403` | 第一步（无令牌）或令牌失效；`data` 里是新令牌 |
| `404` | 任务不存在或已被删除（第二次用同一令牌也会得到这个） |

**请求数据样例**

```json
{ "version": 0 }
```

**响应数据样例**

| `404` | 任务不存在 |
| `409` | `version` 不匹配 |

- **接口名称**：取消任务
- **接口描述**：把任务改为 `CANCELLED`。`TODO` 和 `DOING` 都可以取消。
- **请求路径**：`/api/v1/tasks/{id}:cancel`
- **请求方式**：`POST`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |

| `version` | number | 是 | 乐观锁版本号（请求体） |

**响应参数说明**（`data` 内部）：取消后的完整 [Task](#任务对象下文多处引用)，`status` 为 `CANCELLED`。

**响应数据样例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
    "title": "交季度报告",
    "status": "CANCELLED",
    "priority": "URGENT",
    "pinned": false,
    "tags": ["work"],
    "version": 4,
```

### 3.10 任务历史查询

- **接口名称**：任务历史查询
- **接口描述**：查询一个任务的全部修改记录（审计日志），按时间倒序，最新的在最前面。
- **请求路径**：`/api/v1/tasks/{id}/history`
- **请求方式**：`GET`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 说明 |
|---|---|---|
| `action` | string | 操作类型：`CREATE` / `UPDATE` / `COMPLETE` / `START` / `REOPEN` / `CANCEL` / `DELETE` |
| `actor` | string | 操作人，取自 `X-Actor`，默认 `anonymous` |
| `traceId` | string | 调用方 trace 号，可能为空 |
| `before` | string | 修改前的任务快照，**JSON 字符串**（需要再解析一次）；新建时为空 |
| `after` | string | 修改后的任务快照，JSON 字符串；删除时为空 |

**响应数据样例**

```json
  "data": [

    },
    {
      "action": "CREATE",
      "actor": "agent",
      "traceId": null,
      "after": "{\"id\":\"6f1c0e2a-...\",\"title\":\"交季度报告\",\"version\":0}",
      "at": "2026-11-05T09:12:31+08:00"
    }
  ]
}
```

**错误情况**：任务不存在返回 `404`。

## 四、任务依赖

> 依赖方向：A 依赖 B 记为 `A dependsOn B`，表示 **B 是 A 的前置任务，B 完成前 A 不能完成**。

### 4.1 前置任务列表查询

- **接口名称**：前置任务列表查询
- **接口描述**：查询某个任务依赖的所有前置任务 id。
- **请求路径**：`/api/v1/tasks/{id}/dependencies`
- **请求方式**：`GET`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id（路径参数） |

**响应参数说明**：`data` 是**字符串数组**，元素为前置任务 id，按字典序排序；没有依赖时是 `[]`。

**响应数据样例**

```json
{
  "code": 0,
  "message": "success",
  "data": [
    "9b2c7f80-1a3e-4e25-8b6c-2f9c1d4a5e70",
    "c3d4e5f6-a7b8-4c9d-8e0f-1a2b3c4d5e6f"
  ]
}
```

> 任务不存在时返回 `200` + `[]`（该任务没有任何依赖）。

---

### 4.2 新增前置任务

- **接口名称**：新增前置任务
- **接口描述**：给任务 A 添加一个前置任务 B。**如果会形成循环依赖，请求会被拒绝。**
- **请求路径**：`/api/v1/tasks/{id}/dependencies`
- **请求方式**：`POST`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id（路径参数） |
| `dependsOnId` | string | 是 | 前置任务 id（请求体） |

**响应参数说明**：`data` 是**字符串数组**，为添加成功后的完整前置任务 id 列表。

**请求数据样例**

```json
{ "dependsOnId": "9b2c7f80-1a3e-4e25-8b6c-2f9c1d4a5e70" }
```

**响应数据样例**（HTTP 201）

```json
{
  "code": 0,
  "message": "success",
  "data": ["9b2c7f80-1a3e-4e25-8b6c-2f9c1d4a5e70"]
}
```

**业务规则与错误**

| 状态码 `code` | 场景 |
|---|---|
| `201` | 成功；**已有该依赖时也返回 201（幂等）** |
| `400` | `dependsOnId` 为空 |
| `404` | 任务或前置任务不存在 |
| `422` | 会形成环（如已有 A→B、B→C，再建 C→A）；或自己依赖自己。`message` 会说明 |

---

### 4.3 删除前置任务

- **接口名称**：删除前置任务
- **接口描述**：移除任务 A 对任务 B 的依赖关系。
- **请求路径**：`/api/v1/tasks/{id}/dependencies/{dependsOnId}`
- **请求方式**：`DELETE`
- **响应格式**：无响应体（`204`）

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id（路径参数） |
| `dependsOnId` | string | 是 | 前置任务 id（路径参数） |

**响应参数说明**：无，HTTP `204` 无响应体。

**响应数据样例**：无（`204 No Content`）

**业务规则与错误**

| 状态码 `code` | 场景 |
|---|---|
| `204` | 已删除；**依赖本来就不存在时同样返回 204（幂等）** |

## 五、批量操作

### 5.1 批量修改任务

- **接口名称**：批量修改任务
- **接口描述**：一次修改多个任务，**要么全部成功，要么全部不生效**（事务）。
- **请求路径**：`/api/v1/tasks:batch`
- **请求方式**：`POST`
- **响应格式**：`application/json`

> ⚠️ 注意路径是 `tasks:batch`，中间**没有斜杠**。写成 `/api/v1/tasks/:batch` 会 404。

**请求参数说明**（请求体 `application/json`）

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `ops` | array | 是 | 要修改的任务列表，至少 1 条 |

**`ops` 元素说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 id |
| `version` | number | 是 | 该任务的乐观锁版本号 |
| `patch` | object | 否 | 要改的字段，字段同 [3.4 修改任务](#34-修改任务) 的请求体（**不含 `version`**） |

**响应参数说明**（`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| `applied` | number | 实际修改成功的条数（全部成功时等于 `ops` 长度） |
| `ids` | array\<string\> | 被修改的任务 id 列表 |

**请求数据样例**

```json
{
  "ops": [
    { "id": "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11", "version": 2, "patch": { "startAt": "2026-11-09T10:00:00+08:00" } },
    { "id": "9b2c7f80-1a3e-4e25-8b6c-2f9c1d4a5e70", "version": 0, "patch": { "priority": "LOW" } }
  ]
}
```

**响应数据样例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "applied": 2,
    "ids": [
      "6f1c0e2a-6f9a-4c1d-9d0e-3c5b8a7f2b11",
      "9b2c7f80-1a3e-4e25-8b6c-2f9c1d4a5e70"
    ]
  }
}
```

**业务规则与错误**

| 状态码 `code` | 场景 |
|---|---|
| `200` | 全部成功 |
| `400` | `ops` 为空、某条的 `id`/`version` 缺失 |
| `404` | 某条任务不存在 |
| `409` | 任一任务 `version` 不匹配 → **整批回滚，一条都没改** |

| 参数名 | 类型 | 是否必填 | 说明 |

| `to` | string | 是 | 查询区间终点，ISO-8601 带偏移 |

| 参数名 | 类型 | 说明 |

### 7.1 发送对话

- **接口名称**：发送对话
- **接口描述**：提交一句用户消息，服务端启动一次 Agent 循环，并返回本次对话的 `streamId`，用于订阅事件流。
- **请求路径**：`/chat`
- **请求方式**：`POST`
- **响应格式**：`application/json`

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `sessionId` | string | 是 | 会话 id，由前端生成（如 `s_<uuid>`），同一会话复用 |
| `message` | string | 是 | 用户消息原文，1-2000 字 |

**响应参数说明**（`data` 内部）

| 参数名 | 类型 | 说明 |
|---|---|---|
| `streamId` | string | 事件流 id，用于 `GET /stream/{streamId}` |
| `traceId` | string | 本次对话的 trace 号，可查 `GET /trace/{traceId}` |
| `degraded` | boolean | 是否降级（主模型不可用、切换到备用模型时为 `true`） |

**请求数据样例**

```json
{
  "sessionId": "s_7d2f4a0e",
  "message": "我这周发烧，周三到周五干不了活，帮我重排一下"
}
```

**响应数据样例**（HTTP 202）

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "streamId": "st_9c1e2f3a",
    "traceId": "tr_4b5c6d7e",
    "degraded": false
  }
}
```

> **关于 `degraded` 的时序（实现后补充说明）**：202 返回时，路由和模型调用都还没开始，
> 所以这个字段只表示**启动时已知的降级**（例如没配推理模型）。
> 本轮是否真的降级，以 `done` 事件的 `degraded` 为准。
> 前端不要用 202 的 `degraded` 做最终判断。

**`degraded` 为 `true` 的三种情形**（都在 `done.degradeReason` 里给出原因）：

| 原因 | 触发 |
|---|---|
| `reason_model_unavailable:*` | 推理模型超时/熔断，已切换到 fast 策略重做本轮 |
| 未配置 `DEEPSEEK_API_KEY` | 静态降级，全程使用备用模型 |

### 7.2 订阅事件流

- **接口名称**：订阅事件流
- **接口描述**：以 SSE（`text/event-stream`）方式订阅一次对话的实时事件：逐字回复、工具调用、待确认操作、结束。
- **请求路径**：`/stream/{streamId}`
- **请求方式**：`GET`
- **响应格式**：`text/event-stream`（**这个接口是全文档唯一的例外，不用 `{code,message,data}` 外壳**）

**请求参数说明**

| 参数名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `streamId` | string | 是 | 路径参数，来自 `POST /chat` |

**请求头**

| 请求头 | 含义 |
|---|---|
| `Last-Event-ID` | 断线重连时带上最后收到的事件 id，服务端从该事件之后继续推送（续传） |

**事件说明**

每个事件格式为：`event: <类型>` + `data: <JSON>`，以及 `id: <事件序号>`。

| 事件类型 | `data` 关键字段 | 说明 |
|---|---|---|
| `token` | `text` | 回复文本的一个片段，前端追加显示 |
| `tool_call` | `name`、`args`、`step` | 开始调用一个工具，如 `task.search` |
| `tool_result` | `name`、`ok`、`summary`、`durationMs` | 工具返回 |
| `clarify` | `question`、`options` | 需要用户澄清（一轮只问一个问题） |
| `confirm` | `confirmToken`、`plan`（`moved`/`kept`/`cannotFit` 三组） | 需要用户确认的破坏性操作 |
| `done` | `traceId`、`costYuan`、`degraded` | 本轮结束 |
| `error` | `code`、`message` | 本轮失败，错误码与第八节一致 |

**事件样例**

```text
event: tool_call
id: 3
data: {"name":"task.search","args":{"keyword":"发烧"},"step":2}

event: token
id: 4
data: {"text":"我把 3 个"}

event: confirm
id: 9
data: {"confirmToken":"cf_...","plan":{"moved":[{"id":"6f1c...","from":"2026-11-05T14:00:00+08:00","to":"2026-11-09T10:00:00+08:00"}],"kept":[],"cannotFit":[]}}

event: done
id: 10
data: {"traceId":"tr_4b5c6d7e","costYuan":0.004,"degraded":false}
```

**错误情况**：`streamId` 不存在返回 `404`（此时仍走统一外壳）。

**实现补充（SP2）**：

- `error` 事件除了第八节的错误码，还会出现 `code: "DEGRADED"`（降级提示，本轮继续）
  和 `code: "INTERNAL_ERROR"`（本轮中止）。
- **被护栏拦下的调用也会推 `tool_call` + `tool_result`**，`tool_result.ok=false`，
  并在 `code` 字段给出错误码（如 `TASK_ID_NOT_IN_CONTEXT`）。
  这样前端时间线上不会缺一格——"尝试过但被拦下"本身就是重要信息。
- `done` 事件额外带 `endedBy`（`finish` / `clarify` / `confirm` / `aborted` / `error`）、
  `steps`（实际步数）、`actionsTaken`（真的执行过的动作），供前端和评测使用。
- **L2 补充（韧性层）**：
  - `done` 的 `degraded` / `degradeReason` 是**判定是否降级的唯一依据**；降级原因形如
    `reason_model_unavailable:LLMTimeout`、`single_step_fallback:LLMUnavailable`。
  - `done` 新增 `suggestions`（结构化下一步，`[{hint, reason}]`，可能为空数组）、
    `promptVersion`（本轮实际使用的 prompt 版本，L4 报告头必须记录）、
    `errorCode`（本轮出现过的错误码；`aborted` 时非空，`DEGRADED` 不算）。
  - `error` 事件新增 `suggestions`，且 `message` 已做**人话转译**：
    `NOT_IMPLEMENTED(501)` / `UPSTREAM_UNAVAILABLE(503)` 不会把上游原始文案透给用户。
    `code` 字段保持原样（评测按码统计），前端展示请用 `message`。
  - 三层降级都会写 trace 的 `kind=DEGRADE` 行（`name` = `llm.degrade_l1` /
    `llm.degrade_l2` / `llm.degrade_l2_failed` 等），`detail.error` 带原因。
- **L3 补充（并发层）**：
  - `POST /chat` 在**入口准入队列已满**（默认 64）时直接返回 `503`
    （`data.errorCode = "OVERLOADED"`），**不排队等待**；客户端应退避后重试。
  - 同一会话的上一轮还没结束时，第二条消息会在会话锁上最多等 20s；
    超时后该 stream 推 `error {code: "SESSION_BUSY"}` 并以
    `done {endedBy: "busy", errorCode: "SESSION_BUSY"}` 收尾。错误码语义对应 409；
    因 `/chat` 已 202，实际经 SSE `error` 表达（HTTP 响应本身仍是 202）。
    其它会话不受影响。
  - 整轮超过 `turn_timeout_s`（默认 60s）→ `done {endedBy: "timeout", errorCode: "TURN_TIMEOUT"}`；
    看门狗会在同一时刻把该 trace 的协程栈写到日志（只打印，不取消）。
  - 缓冲区在内存里，服务重启后旧 `streamId` 会 404（`Last-Event-ID` 续传只在同一进程生命周期内有效）。

## 八、错误码总表

所有失败响应都是 `{code, message}`，`code` 等于 HTTP 状态码：

| `code` | 类型名（内部） | 含义 | 前端处理建议 | 可重试 |
|---|---|---|---|---|
| `0` | — | 成功 | — | — |
| `400` | `VALIDATION_ERROR` | 请求参数不合法（缺失、格式错误、越界、JSON 解析失败、参数类型不对） | 提示字段错误，修改后重发 | ✅ 改参数后 |
| `403` | `CONFIRM_REQUIRED` | 删除需要确认令牌（两阶段删除的第一步） | 弹确认框，拿 `data.confirmToken` 再调 | ✅ 带令牌后 |
| `404` | `NOT_FOUND` | 任务不存在 / 已删除 / 接口路径写错 | 提示并刷新列表 | ✅ 改 id 后 |
| `405` | `VALIDATION_ERROR` | 方法不允许（如对 GET 接口发 POST） | 检查请求方法和路径 | ❌ 修前端 |
| `409` | `CONFLICT` | `version` 不匹配：任务在你读取之后被别人改过 | 重新查询拿最新 `version` 再重试 | ✅ 刷新后 |
| `422` | `ILLEGAL_TRANSITION` | 状态机不允许该操作（如对已完成任务调「开始」） | 告知用户正确操作顺序（先「恢复」） | ❌ |
| `422` | `DEPENDENCY_VIOLATION` | 依赖不满足：会成环，或前置任务未完成 | 告知用户调整依赖关系 | ❌ |
| `500` | `INTERNAL_ERROR` | 服务端未预期错误 | 提示「服务异常，请稍后再试」并上报 `traceId` | ✅ 稍后 |

> `422` 的两种场景共用同一个状态码，**靠 `message` 区分**（前者说状态，后者说依赖）。
> 前端只需展示 `message`，不需要解析类型名。

## 九、附录

### 9.1 与上一版（v0.1.0）的差异

本版把响应统一成 `{code, message, data}` 外壳，属于**破坏性变更**：

| 变化 | 旧 | 新 |
|---|---|---|
| 成功响应 | 直接返回业务对象 `{"items":[...]}` | `{"code":0,"message":"success","data":{"items":[...]}}` |
| 错误响应 | `{"code":"CONFLICT","message":"...","recoverable":true,...}` | `{"code":409,"message":"..."}` |
| 删除第一步的令牌 | `suggestions[0].value` | `data.confirmToken`（另有 `expiresInSeconds`、`snapshot`） |
| 204 响应 | 无 body | 不变，仍无 body |

**v0.1.0 的 `recoverable` / `suggestions` / `details` 字段不再出现在响应里**：
它们是给服务端日志、trace 与 Agent 决策用的内部信息。前端的「能不能重试」判断改为按第八节的
「可重试」列：`409` 刷新后重试，`422` 不重试，`500` 稍后重试。

### 9.2 尚未覆盖的已知问题（开发时需要知道）

| # | 问题 | 影响 | 处理时机 |
|---|---|---|---|
| 1 | 批量修改不写审计日志 | 任务历史的 `action` 目前不会出现 `BATCH_UPDATE` | 排期再补 |
| 2 | 忙闲查询只考虑任务占用 | 不含会议、通勤等外部忙碌 | Agent 侧 `working_hours` 配置补齐 |
| 3 | 删除任务不校验 `version` | 只靠确认令牌防误删 | 当前设计如此，暂不改 |
| 4 | 幂等键并发无保护 | 极端并发下同键可能建两条 | 上线前加唯一约束 |
| 5 | `PATCH` 无法把字段清空 | 传 `null` 表示「不修改」 | 后续版本加显式清除语义 |
| 6 | 删除任务后不能对其加依赖 | 两阶段删除之后，加依赖会返回 404 | 属于预期行为 |
| 7 | Agent 相关接口尚未实现 | 第七节全部为设计稿，联调前需先完成 SP2 | SP2 |
